Layer 3 design decisions (draft)

Working notes for Stage A — Task 5. Each section is an open question with options and a current lean. Locked decisions move into the Overview once agreed.

Refs #352. L2 components are locked (see Components Overview). L3 sits between the public API and L2: it owns workflows, constraints, and transactions.

1. Workflow granularity​

Question. Is "one workflow per user action" the right unit, or should related actions be grouped?

Context. The user-actions inventory lists ~150 distinct actions across 14 domains. Many are trivial CRUD on master data (Create material, Update material, Delete material). A few are heavy (PO receipt cascade, WO completion, SO fulfillment).

Options.

  • A. One workflow per write action. Mirrors the user-actions inventory 1:1. Verbose but unambiguous — every public endpoint maps to a single workflow.
  • B. One workflow per resource cluster. Group CRUD (createCustomer + updateCustomer + deleteCustomer → one CustomerWorkflow with three operations). Fewer files, but the unit-of-work boundary blurs.
  • C. Hybrid. One workflow per write action for substantive flows (orders, receipts, transfers, cascades). One CRUD-bundle workflow per master-data domain (customers, vendors, materials, etc.) where the three operations share validation rules.

Lean: C. Most master-data CRUD is "validate uniqueness + insert/update/delete + check in-use on delete" — three near-identical workflows would just be ceremony. Substantive flows deserve their own page so the composition + constraints are legible.

Reads. Only document reads as workflows when they do more than "fetch from one component" (e.g., the Home dashboard bundle composes 8+ component reads; SO detail enriches with computed fulfillment status). Pure pass-through reads belong at L4, not L3.

2. Constraint location​

Question. What lives in L3 vs. L4 vs. the database?

Options / current thinking.

  • L4 (request validation). Shape, types, required fields, format (Zod schemas). Stops malformed input before it reaches a workflow.
  • L3 (business rules). Cross-entity rules: "can't delete a customer type still in use", "can't transition PO from Paid back to Planning", "WO receipt quantity can't exceed expected". Anything that needs to read from one or more L2 components to decide.
  • DB (integrity). FKs, NOT NULL, UNIQUE, CHECK. Last line of defence — if L3 forgets, the DB still says no.

Lean. Same split as above. L3 is where domain rules live, not L4 (which stays a thin protocol layer) and not L2 (which stays a thin data layer).

3. Workflow structure (file + signature)​

Question. What does a workflow look like in code?

Options.

  • A. Function per workflow. backend/src/l3/purchase-orders/create-purchase-order.ts exports createPurchaseOrder(input, ctx). One file per workflow.
  • B. Module per domain. backend/src/l3/purchase-orders.ts exports createPurchaseOrder, updatePurchaseOrder, etc. Smaller surface; cluster-related rules can share helpers.
  • C. Class per domain. Same shape as B, but as a class with injected component dependencies. Easier to mock for tests.

Lean: B. Functions are simpler than classes; we already do dependency-light wiring at L2. One file per workflow (A) would mean ~80 files; a module per domain keeps the count near L2's (~15).

Signature shape. Every workflow:

  • Takes a typed input (no req, no HTTP).
  • Takes a ctx: { orgId, userId, pool } — opens its own transaction via withTransaction(pool, orgId, ...).
  • Returns a typed result (or throws a typed error).

4. Transaction boundary​

Settled in L2. L3 owns the unit of work; L2 ops accept a Queryable and never open transactions.

Implication. A workflow opens exactly one withTransaction at the top, then calls into one or more L2 components with the resulting client. If a workflow composes another workflow (rare — see §1), the composed workflow takes the client instead of the pool.

Open: read-only workflows. Use withConnection (no BEGIN) when the workflow only reads.

5. Error model​

Question. How do workflows signal business-rule failures?

Options.

  • A. Typed exceptions. throw new InUseError(...) / throw new InvalidTransitionError(...). L4 maps to HTTP status. Familiar, but exceptions for control flow.
  • B. Result type. Workflow returns Ok<T> | Err<L3Error>. Explicit, but verbose in TS.
  • C. Status-tagged return. { ok: true, value } | { ok: false, code, message }. Same idea as B, simpler shape.

Lean: A. Existing codebase already throws; adding a Result type now means rewriting every caller. A small L3Error base class with subclasses (NotFoundError, InUseError, InvalidTransitionError, ValidationError) gives L4 a clean mapping table without ceremony in the workflow body.

6. Cost cascade — workflow or sub-step?​

Question. Is "cascade costs" its own workflow, or a sub-step composed by other workflows?

Context. Today cost-cascade.ts exports three functions called from PO-receipt create/update/delete, PO-cost recalc, and WO item updates. The cascade reads from po_receipt_items, bom_items, materials_inventory_ledger, and writes to materials_inventory_ledger, work_order_items, finished_goods_inventory_ledger — five domains.

Options.

  • A. Standalone workflow. cascadeCostsFromPO(orgId, poId, ctx) — composed by every workflow that mutates upstream costs.
  • B. Inlined per call site. Each receipt/WO workflow has its own cascade logic. Duplication; tightly couples receipts and WO updates.
  • C. Sub-workflow. A "private" workflow not exposed at L4 — only callable from other L3 workflows. Same as A in practice; just labelled differently.

Lean: A/C. Same code shape — a workflow that other workflows call, never exposed at L4. The cascade is a real unit of work (rebuilds MI ledger entries, recomputes WO material unit costs, updates FG ledger entries) and deserves a single home.

7. Anthem-specific data​

Question. Where do Anthem-specific values live — branding (logo, colors), PO PDF templates, billing address, copy strings?

Options.

  • A. L3 template config. Hardcoded in backend/src/l3/templates/anthem/. Per-template directory; new templates copy + override.
  • B. Per-org settings. Stored in organization_settings (already exists). The "Anthem template" is the default seed values for a new org; admins edit from Settings.
  • C. Static assets keyed by template ID. PDFs/images served from static/templates/anthem/, rows in DB only store template ID + asset filenames.

Lean. Open. Likely a split: copy + structural template choices = A; per-org overridable values (billing address, logo) = B; binary assets = C. Needs a closer look at what's actually Anthem-specific today.

8. Background workers / cron / async​

Question. Are there any background workers, cron jobs, or async processes today?

To audit. setInterval, node-cron, queue libs (bullmq, agenda), GCP Cloud Tasks usage, anything fire-and-forget at the request boundary.

Known async-shaped flow. Invitation emails — sent via the invite workflow but the email send itself may be best-effort vs. transactional.

If none exist today. L3 workflows are all request-driven; no workers/ sub-tree until something needs it.

9. Idempotency​

Question. Do any workflows need idempotency keys?

Lean. Out of scope for Stage A unless we find a concrete duplicate-submission risk in the inventory. Bulk imports may need it; revisit per workflow.
