Purchase Orders

Workflows for purchase orders, their line items, and receipts. POs target either materials (raw inputs) or finished goods (resale), set on creation and immutable thereafter. Receipt workflows touch two domains at once: they write the PO-side receipt and the matching inventory ledger entries in the same transaction, and — for materials POs — propagate cost changes downstream through work orders and finished-goods inventory.

Composes: PurchaseOrders, MaterialsInventory, FinishedGoodsInventory, Vendors, Materials, Products, Locations, BOM, WorkOrders, OrganizationSettings.

Status transitions are governed by a per-org table (po_status_types) plus a fixed manual-transition map seeded with: Planning → Placed | In Transit | Cancelled, Placed → In Transit | Cancelled, In Transit → Cancelled, Received → Paid, Partial / Paid / Cancelled → terminal. Automatic transitions (e.g., Placed → In Transit once an ORDER entry exists, Received once cumulative receipts equal expected quantities) are computed by the receipt workflows.

Writes​

1. Create purchase order​

Triggered from the Purchase Orders page → "New PO" button.

Composes: PurchaseOrders, Vendors, Locations, plus MaterialsInventory or FinishedGoodsInventory for the initial ORDER entries.

Steps:

  1. Generate the next PO number (PO-001, PO-002, …) using the global counter for the org. Numbers are unique per org, monotonically increasing.
  2. Verify referenced rows belong to this org: Vendors.getById, Locations.getById. Reject if either is missing or soft-deleted.
  3. PurchaseOrders.createPo with header fields and initial status (Planning by default).
  4. For each line item: PurchaseOrders.addItem with the material or SKU id (must match the PO's targetType) and unit cost.
  5. If status is Placed or beyond at creation time, write one ORDER ledger entry per line — MaterialsInventory.recordOrder for materials POs, FinishedGoodsInventory.recordOrder for finished-goods POs — with ref = poNumber.

Returns: the new PO with hydrated items.

Business rules:

  • targetType is fixed at creation; line items must reference the matching catalog (materials xor SKUs).
  • Vendors and ship-to locations must be active.
  • Status must be one of the org's configured po_status_types.

Errors:

  • NotFoundError — vendor / location / referenced material or SKU not found.
  • ValidationError — line item references the wrong catalog for the target type, or status not configured.

2. Update purchase order​

Triggered from the Purchase Order Detail page.

Composes: PurchaseOrders, plus the relevant inventory component when status transitions trigger ledger writes.

Steps:

  1. PurchaseOrders.getPoById — confirm existence and load current state.
  2. If the patch changes status, validate the transition against the manual map. The PO statuses set on creation, Partial and Received are reachable only through receipt workflows — they are not accepted here.
  3. If the patch transitions to Placed (from Planning) and no ORDER entries exist yet, insert them now: one per line via the appropriate inventory component's recordOrder, ref = poNumber.
  4. If the patch transitions to Cancelled, delete any ORDER entries for this PO (listEntries({ refLike: poNumber }), filter by event type, then deleteEntry). Existing RECEIVE entries stay — they record real movements.
  5. PurchaseOrders.updatePo with the patch.

Returns: the updated PO.

Business rules:

  • targetType, number, and orderDate are immutable.
  • vendorId and shipToLocationId are editable only while in Planning.
  • Transitioning to Cancelled is allowed at any non-terminal state and reverses ORDER entries but not RECEIVE entries (those represent inventory that physically arrived).

Errors:

  • NotFoundError — PO not found.
  • InvalidTransitionError — status change not in the manual map, or attempted entry of a receipt-only status.
  • ValidationError — editing a header field that is immutable in the current status.

3. Delete purchase order​

Triggered from the Purchase Order Detail page.

Composes: PurchaseOrders, MaterialsInventory or FinishedGoodsInventory.

Steps:

  1. PurchaseOrders.getPoById — confirm existence.
  2. MaterialsInventory.listEntries({ refLike: poNumber }) (or FG counterpart) — collect every ledger entry tied to this PO.
  3. For each ledger entry, deleteEntry. This reverses both ORDER and RECEIVE effects on inventory.
  4. For a materials PO that had RECEIVE entries, run the downstream cascade (see §8 steps 5–7) to roll back work-order material unit costs and FG ledger ORDER/RECEIVE costs that referenced this PO.
  5. PurchaseOrders.deletePo — cascades to items, receipts, receipt items.

Returns: nothing.

Business rules:

  • Deleting a PO is permitted at any status; the workflow exists to wipe a record cleanly. UI gates terminal-state deletion separately.
  • For FG-target POs the cascade is unnecessary — FG RECEIVE entries don't feed any further downstream cost.

Errors:

  • NotFoundError.

4. Bulk-import purchase orders​

Triggered from the Data page → POs import.

Composes: same as Create plus an upload parser.

Steps:

  1. Parse the uploaded CSV/Excel into rows of { header, items[] }. Per-row parse errors are collected, not thrown — the whole import succeeds or fails atomically below.
  2. If any rows failed to parse, abort with a ValidationError listing the failures.
  3. Inside a single withTransaction, for each row: run the Create PO workflow's steps 1–4 (number, validate refs, createPo, addItem). ORDER entries are written in step 5 only for rows whose initial status implies them.
  4. Commit. On any failure the entire batch rolls back.

Returns: the list of created PO numbers.

Business rules:

  • Atomic — all rows or none. Partial imports are not supported (and would leave the user reconciling which rows landed).
  • PO numbers in the file are advisory; the workflow always generates fresh ones to avoid colliding with the org's counter.

Errors:

  • ValidationError — parse failures, or any single row failing the Create PO rules.

5. Add item to purchase order​

Triggered from the Purchase Order Detail items section.

Composes: PurchaseOrders, Materials or Products, plus the relevant inventory component if the PO is past Planning.

Steps:

  1. PurchaseOrders.getPoById — confirm existence and read targetType and status.
  2. Verify the referenced material or SKU exists in this org, matches targetType, and is active.
  3. PurchaseOrders.addItem with quantity and unit cost.
  4. If the PO is at Placed or beyond, write one ORDER ledger entry for the new line via recordOrder, ref = poNumber.

Returns: the new line.

Errors:

  • NotFoundError — PO, material, or SKU not found.
  • ValidationError — referenced catalog mismatches the PO's target type.

6. Update purchase order item​

Triggered from the Purchase Order Detail items section.

Composes: PurchaseOrders, plus the inventory component if quantity or unit cost changes propagate to the ledger.

Steps:

  1. PurchaseOrders.getItemById — confirm existence and read the parent PO.
  2. If the patch changes materialId or skuId, the new reference must still match the parent's targetType.
  3. PurchaseOrders.updateItem with the patch.
  4. If the PO already has ORDER entries for this line (status ≥ Placed) and the patch changed quantity or unit cost, delete and re-insert the corresponding ORDER entry to keep the ledger in sync.
  5. If the PO has RECEIVE entries against this line and unit cost changed, run the downstream cost cascade (see §8 steps 5–7) — the WO material-cost rollup uses ledger unit costs, which now need to be reflected on every dependent WO item and FG ledger entry.

Returns: the updated line.

Errors:

  • NotFoundError.
  • ValidationError — catalog mismatch.

7. Remove item from purchase order​

Triggered from the Purchase Order Detail items section.

Composes: PurchaseOrders, plus the inventory component.

Steps:

  1. PurchaseOrders.getItemById — confirm existence.
  2. Refuse removal if any receipt items reference this line — the user must delete the receipts first.
  3. Delete any ORDER ledger entries for this specific line.
  4. PurchaseOrders.removeItem.

Errors:

  • NotFoundError.
  • InUseError — receipts reference this item.

8. Create receipt against purchase order​

Triggered from the Purchase Order Detail receipts section. The most substantive workflow in this domain — writes the PO-side receipt, the matching inventory ledger entries, and (for materials POs) propagates the receipt's unit costs downstream through every work order that consumes the affected materials.

Composes: PurchaseOrders, MaterialsInventory or FinishedGoodsInventory, plus BOM, WorkOrders, FinishedGoodsInventory again for the cascade.

Steps:

  1. PurchaseOrders.getPoById — confirm PO exists; capture targetType, poNumber, and shipToLocationId.
  2. Validate that the PO is not in a terminal status (Paid, Cancelled) — receipts are not allowed after.
  3. PurchaseOrders.createReceipt with the receipt date and notes.
  4. For each received line in the input: PurchaseOrders.addReceiptItem and one ledger insert via MaterialsInventory.recordReceipt (materials PO) or FinishedGoodsInventory.recordReceipt (FG PO). ref = poNumber, locationId = shipToLocationId, unitCost taken from the receipt input (defaults to the PO line's unit cost if unspecified).
  5. Recompute the PO's status: if cumulative received quantities meet or exceed every line's expected quantity, transition to Received; otherwise transition to Partial. PurchaseOrders.updatePo accordingly.
  6. Materials cascade (skip for FG POs). Collect the set of materialIds touched by this receipt. For each material, recompute its weighted-average unit cost across all RECEIVE entries in the ledger.
  7. Materials cascade — WO update. For every work_order_items row whose SKU has a BOM input referencing any of those materials, recompute material_unit_cost as Σ (bom_input.quantity × avg_unit_cost_for_input). WorkOrders.updateItem (or a dedicated setMaterialUnitCost op) writes the new value.
  8. Materials cascade — FG ledger update. For every affected work order, update the unit cost on its ORDER and RECEIVE entries in finished_goods_inventory_ledger to (material_unit_cost + conversion_cost), keyed by (ref = wo_number, sku_id).

Returns: the new receipt with its received-item rows.

Business rules:

  • Received quantities must be non-negative and may exceed the line's expected quantity (the workflow allows over-receipt; the PO simply ends in Received rather than Partial).
  • Step 3's RECEIVE entries and step 5's status update are inside the same transaction as the cascade — partial cascade visibility is impossible.
  • For FG POs the cascade is skipped because finished-goods receipts have no further downstream cost dependents.

Errors:

  • NotFoundError.
  • InvalidTransitionError — PO is in a terminal status.
  • ValidationError — receipt line references a poItemId that isn't on this PO.

9. Update receipt​

Triggered from the Purchase Order Detail receipts section. Allows editing date, notes, or received quantities. Re-runs steps 4–8 from §8 if quantities or costs change.

Composes: same as Create receipt.

Steps:

  1. PurchaseOrders.getReceiptById — confirm and read the parent PO.
  2. If only date / notes changed, PurchaseOrders.updateReceipt and return.
  3. Otherwise: delete the existing RECEIVE ledger entries for this receipt (listEntries filtered by ref = poNumber joined to this receipt's items), update the receipt and its items, re-create the RECEIVE entries, and re-run steps 5–8 from §8.

Returns: the updated receipt.

Notes:

  • Rebuilding the ledger entries (rather than patching them) keeps the cascade in step 6 honest — the weighted-average recompute reads whatever is currently in the ledger and produces the correct new state.

Errors:

  • NotFoundError.
  • InvalidTransitionError — PO is terminal.

10. Delete receipt​

Triggered from the Purchase Order Detail receipts section.

Composes: same as Create receipt.

Steps:

  1. PurchaseOrders.getReceiptById — confirm existence.
  2. Delete every ledger entry tied to this receipt (one per receipt-item, identified by ref = poNumber + materialId/skuId + receipt date heuristic, or via a dedicated lookup — see L1 follow-up notes).
  3. PurchaseOrders.deleteReceipt — cascades to receipt items at the PO side.
  4. Recompute the PO status: if no RECEIVE entries remain for this PO, transition back to Placed (or In Transit if the prior state was that); if some remain, recompute Partial vs Received per §8 step 5.
  5. For materials POs, re-run the cascade (steps 6–8 of §8) — material averages and downstream costs need to reflect the deletion.

Errors:

  • NotFoundError.

11. Create PO status type​

Triggered from Settings → PO status types.

Composes: PurchaseOrders.

Steps:

  1. Verify the name is unique within this org (case-insensitive, trimmed).
  2. Compute sortOrder under an advisory lock to avoid concurrent collisions (the L2 op does this already).
  3. Insert the row with the requested colors.

Errors:

  • ValidationError — duplicate name.

12. Update PO status type​

Triggered from Settings → PO status types.

Composes: PurchaseOrders.

Steps: load the row, check name uniqueness if name changed, write the patch.

Errors: NotFoundError, ValidationError.

13. Delete PO status type​

Triggered from Settings → PO status types.

Composes: PurchaseOrders.

Steps:

  1. Count POs currently in this status via listPos({ status: name }).
  2. If any exist, refuse.
  3. Soft-delete (or hard-delete — schema choice) the status row.

Errors:

  • InUseError — POs reference this status.

Reads​

14. List purchase orders​

Triggered from the Purchase Orders page.

Composes: PurchaseOrders, optionally Vendors for header enrichment.

Steps:

  1. PurchaseOrders.listPos(filters).
  2. Batch-hydrate vendors via Vendors.listByIds to enrich each row with vendor name (avoids N+1 at L4).

Returns: PO header rows with vendor name attached.

15. Get purchase order detail​

Triggered by clicking a PO.

Composes: PurchaseOrders, Vendors, Locations, Materials or Products (depending on targetType).

Steps:

  1. PurchaseOrders.getPoById.
  2. Batch-load items, vendor, ship-to location, and the catalog rows referenced by the items.
  3. Merge into a single hydrated view.

16. List items across purchase orders​

Triggered from cross-PO views (reporting, lookups by material/SKU).

Composes: PurchaseOrders.

Steps: PurchaseOrders.listAllItems(filters).

17. List items for a purchase order​

Triggered from Purchase Order Detail.

Composes: PurchaseOrders.

Steps: PurchaseOrders.listItemsByPo(poId).

18. List receipts for a purchase order​

Triggered from Purchase Order Detail.

Composes: PurchaseOrders.

Steps: PurchaseOrders.listReceiptsByPo(poId).

19. Get receipt detail​

Triggered by clicking a receipt.

Composes: PurchaseOrders.

Steps: PurchaseOrders.getReceiptById + listReceiptItems.

20. Generate PO PDF​

Triggered from Purchase Order Detail → "Export PDF". Composes a printable PO document from header, items, vendor, ship-to, and the org's branding / billing.

Composes: PurchaseOrders, Vendors, Locations, Materials / Products, OrganizationSettings, Contacts (for vendor contact lookup).

Steps:

  1. Hydrate everything Get Detail (§15) returns.
  2. Vendors.getById and Contacts.listByEntity(vendorId) — pull the vendor's primary billing contact.
  3. OrganizationSettings.get — read the org's logo (resolves to a Documents row), billing address, and any per-org branding values.
  4. Render the PDF using the generic CPG template fed with the data above. The template is generic; per-org values come entirely from settings.
  5. Return the PDF bytes (the L4 layer streams them to the client).

Notes:

  • No Anthem-specific values appear in this workflow. The template is shape-only; org settings provide the data.

21. List PO status types​

Triggered from filters / status selectors / Settings.

Composes: PurchaseOrders.

Steps: load active status types in sortOrder.

22. Check if PO status type is in use​

Triggered before deleting a status type.

Composes: PurchaseOrders.

Steps: count POs in the status; return { inUse: count > 0, count }.
