Version: Stage A

Platform

Workflows for identity, organization lifecycle, membership, invitations, and the Home dashboard bundle. Sit between the public API and the Platform + OrganizationSettings components. The platform schema is the only place L3 reaches outside a tenant — sign-up and invitation acceptance both create the tenant context that everything else assumes.

External side-effects in this domain: Firebase Authentication (create / delete users), email sending (invitation delivery), and GCS (organization logo). Each is wrapped in its own helper; the workflow stays the unit of work.

Writes​

1. Sign up​

Triggered from the Login / OrgSignup page after the user authenticates with Firebase for the first time.

Composes: Platform.

Steps:

  1. Verify the Firebase ID token and pull out the firebaseUid, email, and display name.
  2. getUserByFirebaseUid — if a row already exists, return it (sign-up is idempotent for repeat first-loads).
  3. Otherwise createUser with the Firebase identity.
  4. listInvitationsByEmail(email, ['pending']) so the next page can prompt the user to accept anything waiting for them.

Returns: the new (or existing) user plus their pending invitations.

Business rules:

  • A firebaseUid is unique across the platform; the L2 createUser op already enforces this at the table level.
  • Sign-up does not create an organization. Org creation is a separate workflow that the OrgSignup page chains immediately after, when the user opted into the "create my own org" path.

Errors:

  • ValidationError — Firebase token invalid or email missing from claims.

2. Log out​

Triggered from the user menu.

Stateless on the server today: Firebase clears its own session in the browser and the next request simply arrives without a valid token. No L2 ops, no DB writes, no workflow body beyond returning { ok: true }. Documented here for completeness so the user-actions inventory stays 1:1 with workflows.

3. Create organization​

Triggered from the OrgSignup or NewOrganization page. The user creating the org becomes its owner.

Composes: Platform, OrganizationSettings.

Steps:

  1. createOrganization with the requested name and a slug derived from the name.
  2. addMembership for the current user with role owner.
  3. OrganizationSettings.upsert with the default seed values (currency, address placeholders, branding defaults).

Returns: the new organization and the owner membership.

Business rules:

  • Slug must be unique across the platform; collision retries by appending a numeric suffix before giving up.
  • The transaction runs without app.org_id (the org doesn't exist yet for the createOrganization line) and then sets it for the OrganizationSettings.upsert line so the new tenant context is in scope for the settings write.

Errors:

  • ValidationError — slug exhausted retries, or name failed shape checks at L4.

4. Update organization​

Triggered from the Organization page. Edits identity fields (name, slug) and the org-level settings bundle (branding, billing address, logo reference) in one round-trip.

Composes: Platform, OrganizationSettings.

Steps:

  1. If the patch includes name or slug, updateOrganization.
  2. If the patch includes any settings field, OrganizationSettings.upsert with just those fields.
  3. If the logo field changed, call OrganizationSettings.updateLogo or clearLogo accordingly — both expect a documents row to already exist for the new logo.

Returns: the merged organization-plus-settings view that the page renders.

Business rules:

  • Only owners and admins can update the organization (enforced at the request boundary; the workflow trusts ctx.userId).
  • Setting a logo requires the document to already exist in the Documents component, owned by the same org.

Errors:

  • NotFoundError — referenced logo document does not exist in this org.
  • ValidationError — slug collision on update.

5. Delete organization​

Triggered from the Organization page (owner only).

Composes: Platform, every tenant-scoped component for the purge.

Steps:

  1. Verify the caller is the org's owner. (Authorization at the request boundary; the workflow re-checks because the blast radius is total.)
  2. Purge tenant rows in dependency order — receipts before items before headers, ledgers before what they reference, settings last — using each component's delete ops. This is the only place L3 sweeps multiple components for a destructive action; the order is encoded explicitly here rather than relying on cascade rules.
  3. deleteOrganization once the tenant tables are empty.
  4. Remove the org's GCS folder (best-effort; logged on failure).

Returns: nothing.

Business rules:

  • Only the org's owner can delete; admins and members cannot.
  • The Firebase users themselves are not deleted — they keep their identities and may belong to other orgs.

Errors:

  • ValidationError — caller is not the owner.

6. Update user role​

Triggered from Settings → Users. Promotes or demotes a member among owner / admin / member.

Composes: Platform.

Steps:

  1. getMembership(targetUserId, orgId) — confirm the target is in this org.
  2. If demoting an owner, count remaining owners; abort if the demotion would leave the org without one.
  3. updateMembershipRole with the new role.

Returns: the updated membership.

Business rules:

  • An org must always have at least one owner.
  • Only owners can change roles. Admins cannot promote themselves or others.

Errors:

  • NotFoundError — target user is not a member of this org.
  • InvalidTransitionError — demotion would orphan the org.

7. Remove user from organization​

Triggered from Settings → Users.

Composes: Platform.

Steps:

  1. getMembership(targetUserId, orgId) — confirm the target is in this org.
  2. If removing an owner, count remaining owners and abort if this would orphan the org.
  3. Reject self-removal — owners and admins must demote first or transfer ownership.
  4. removeMembership.

Returns: nothing.

Business rules:

  • An org must always have at least one owner.
  • A user cannot remove themselves through this workflow (use "leave organization" — not yet implemented; out of scope for v1).

Errors:

  • NotFoundError — target user is not a member.
  • InvalidTransitionError — removal would orphan the org, or caller is removing themselves.

8. Send invitation​

Triggered from Settings → Users → "Invite". Creates a token, persists the invitation, and emails the invitee.

Composes: Platform.

Steps:

  1. getUserByEmail(email) and listInvitationsByEmail(email, ['pending']) — block duplicate pending invites for the same email in this org, and block inviting someone who is already a member.
  2. Generate a random opaque token and an expiry timestamp (default: 7 days from now).
  3. createInvitation with org / email / role / token / expires.
  4. Send the invitation email (subject, accept link with token). Email failure is surfaced but does not roll the invitation back — admins can resend.

Returns: the created invitation.

Business rules:

  • Tokens are single-use and expire; the Accept workflow rejects expired or already-consumed tokens.
  • Only owners and admins can invite.
  • Re-inviting an email that already has a pending invite for this org returns the existing invite (idempotent for the common case of clicking "Invite" twice).

Errors:

  • ValidationError — email already belongs to a member of this org.
  • ValidationError — role is owner (owners are appointed by ownership transfer, not invitation).

9. Resend invitation​

Triggered from Settings → Users → pending invitations row.

Composes: Platform.

Steps:

  1. getInvitationById — confirm it exists, belongs to this org, and is still pending.
  2. touchInvitation — bumps updated_at so the audit trail records the resend.
  3. Re-send the invitation email using the existing token.

Returns: the touched invitation.

Business rules:

  • Resending does not rotate the token or extend the expiry — the invite is the same invite, just delivered again.
  • Out-of-scope optional refinement: extending expiry on resend if it's near the deadline.

Errors:

  • NotFoundError — invitation does not exist in this org.
  • InvalidTransitionError — invitation is accepted, declined, or revoked.

10. Revoke invitation​

Triggered from Settings → Users → pending invitations row.

Composes: Platform.

Steps:

  1. getInvitationById — confirm pending.
  2. updateInvitationStatus(id, 'revoked').

Returns: the revoked invitation.

Business rules:

  • A revoked invitation cannot be undone; admins must send a new one.

Errors:

  • NotFoundError, InvalidTransitionError — same shape as Resend.

11. Accept invitation​

Triggered from the public Accept Invite page after the invitee signs in (or signs up).

Composes: Platform.

Steps:

  1. getInvitationByToken — confirm it exists, is pending, and is not expired.
  2. Confirm the authenticated user's email matches the invitation's email (case-insensitive).
  3. getUserByFirebaseUid — if the platform user record does not exist yet, run the Sign-up workflow inline.
  4. addMembership with the invited role.
  5. updateInvitationStatus(id, 'accepted').

Returns: the new membership and the org details.

Business rules:

  • Email match is required — a token alone is not enough.
  • Accepting flips the invitation to accepted in the same transaction as the membership insert; the two cannot diverge.
  • Re-accepting an already-accepted invitation by the same user is a no-op success; by a different user is an error.

Errors:

  • NotFoundError — token unknown.
  • InvalidTransitionError — invitation expired, declined, revoked, or already accepted by a different user.
  • ValidationError — caller email does not match invitation email.

12. Decline invitation​

Triggered from My Invitations / Accept Invite.

Composes: Platform.

Steps:

  1. getInvitationByToken — confirm pending and not expired.
  2. Confirm the authenticated user's email matches.
  3. updateInvitationStatus(id, 'declined').

Returns: nothing.

Business rules / errors: mirrors Accept, minus the membership insert.

Reads​

13. Get current user​

Triggered on app load.

Composes: Platform.

Steps:

  1. Verify the Firebase token, extract firebaseUid.
  2. getUserByFirebaseUid — return the platform user.
  3. listMembershipsByUser(userId) — return the orgs the user belongs to, with role.

Returns: { user, memberships }.

Notes: this is the only workflow that runs before app.org_id is set. The L4 boundary uses the response to pick (or confirm) an active org and then sets the GUC for every subsequent request in the session.

14. Get organization​

Triggered on every authenticated page.

Composes: Platform, OrganizationSettings.

Steps:

  1. getOrganizationById(ctx.orgId).
  2. OrganizationSettings.get().
  3. Merge: identity fields from the org, branding / billing / logo from settings.

Returns: the merged organization-plus-settings view.

15. List organization users​

Triggered from Settings → Users.

Composes: Platform.

Steps: listMembershipsByOrg(ctx.orgId) — returns memberships joined with user profile fields.

16. List my pending invitations​

Triggered from My Organizations / app login.

Composes: Platform.

Steps:

  1. Resolve the caller's email from the Firebase claims.
  2. listInvitationsByEmail(email, ['pending']).
  3. Filter out anything expired.

Returns: pending, unexpired invitations addressed to the current user's email.

17. List organization invitations​

Triggered from Settings → Users → pending invitations.

Composes: Platform.

Steps: listInvitationsByOrg(ctx.orgId, ['pending']) — outstanding invitations the org has sent.

18. Look up invitation by token​

Triggered from the public Accept Invite page. Unauthenticated.

Composes: Platform.

Steps:

  1. getInvitationByToken.
  2. Return a redacted summary — org name, inviter name, role, expiry. No raw token, no membership data.

Notes: this is the only L3 workflow callable without a tenant context. The L4 boundary skips app.org_id for this route.

Errors: NotFoundError if the token is unknown.

19. Get dashboard​

Triggered from the Home page on app load.

Composes: nearly every domain component — composes existing per-domain read workflows rather than re-querying L2 directly.

Steps:

  1. In parallel: list recent POs, list recent WOs, list recent SOs, get materials inventory summary, get finished-goods inventory summary, list vendors, list status types (PO / WO / SO / fulfillment).
  2. Assemble a screen-specific bundle.

Returns: the bundle the Home page renders in a single round-trip.

Notes:

  • This is the one read workflow that does meaningful composition. The user-actions doc flags it as misplaced (it's a cross-domain concern, not a platform one); when an analytics / reporting domain emerges, this moves.
  • Not an analytics surface. When real analytics land they get their own workflows with proper aggregation pushdowns.
