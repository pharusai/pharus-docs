Workflow review questions

Cross-references the L3 workflow pages against the current backend code (backend/src/db/*, backend/src/routes/*). Round 1 surfaced the questions; the answers below lock the v1.0.0 design.

The overarching call is: the L3 docs describe the v1.0.0 design target. Where the current code diverges, the docs win and code is to be brought into line. Where the docs were thin, this round added the substance.

Round 2 answers (locked)​

#QuestionAnswer
Q-R2-1Cancellation reversal — hard delete or reverse entries?Reverse entries everywhere. PO, WO, and SO cancellations and deletes all append paired negative-quantity rows (REVERSE_ORDER, REVERSE_DEMAND, REVERSE_ALLOCATE, REVERSE_CONSUME, REVERSE_RECEIVE, REVERSE_PRODUCE) rather than hard-deleting originals. The ledger is append-only across all three domains; the audit trail is preserved.
Q-R2-2Cost convention — FIFO or weighted-average?FIFO. Unify on FIFO across CONSUME stamping AND the cost cascade rollup. The W027 cascade computes downstream costs by reading FIFO layers for the next-to-be-consumed quantity, not a flat weighted-average across all RECEIVE entries.
Q-R2-3Transfer model — single-row or paired?Single TRANSFER row with to_location_id plus paired RECEIVE on completion. Code reality kept. The destination is fixed at transfer creation; diverted shipments require cancel-and-recreate.

Round 3 fixes applied​

PO/WO/SO cancellation and delete workflows rewritten to use reverse entries:

  • W021 (PO Cancel), W022 (PO Delete), W028 (PO Update receipt), W029 (PO Delete receipt)
  • W043 (WO Cancel), W044 (WO Delete), W047 (WO Update receipt), W048 (WO Delete receipt)
  • W060 (SO Delete). W059 (SO Update) was already reverse-entries from Round 2.

W027 cost cascade updated to use FIFO weighted-average (fifo_unit_cost_for_input(quantity) returns the average cost of the oldest layers covering the requested quantity). W042 WO creation cost rollup and W046 WO receipt consumption follow the same FIFO convention.

Transfer workflows (W089, W090, W096, W097) rewritten to describe the single-row TRANSFER model with to_location_id and the paired RECEIVE on completion.

Spot-checks against code​

  • Master-data uniqueness. All checked — every type / segment / channel / broker / vendor / material / SKU uniqueness rule is case-insensitive with LOWER(TRIM(name)) in code. The docs say "case-insensitive"; that wording stands.
  • Broker in-use check. Code today only counts customers (isBrokerInUse ignores SOs). The L2 design and W123 doc says the count returns both customerCount and soCount. The doc is the v1.0.0 spec; the code is a known gap to close.

Still open​

Two minor scope questions surfaced from the cancellation/reversal pattern:

Q-R3-1. Reverse event types — formal enum members on both ledgers?

The reverse-entries decision adds new event-type values to both materials and FG ledgers: REVERSE_ORDER, REVERSE_DEMAND, REVERSE_ALLOCATE, REVERSE_CONSUME, REVERSE_RECEIVE, REVERSE_PRODUCE. The L2 inventory component schemas need updating.

Confirm: this is in scope for v1.0.0 implementation (XC1=A already implies "yes, L2 evolves as v1 requires"). The docs assume yes; flagging for visibility.

Q-R3-2. Reverse-entry inventory summary semantics.

When the inventory summary computes onHand, does it net reverse pairs (quantity + reverse = 0) or does it expose them separately so the UI can distinguish "10 units received then 10 reversed" from "0 units"?

  • A: Net them. Summary is the rollup of all entries; reverse pairs simply zero out. Simpler. Cleaner for non-audit views.
  • B: Expose separately. The summary returns received, reversed, netReceived. Heavier read but better audit.

I'll default to A unless told otherwise; B is easy to layer in later if needed.
