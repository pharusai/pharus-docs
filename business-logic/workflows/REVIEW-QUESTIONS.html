Workflow review questions (Round 1)

Collected while cross-referencing every L3 workflow page against the current backend code (backend/src/db/*, backend/src/routes/*). Each question is a design call needed before the docs can be finalized for implementation. Doc-only bugs are listed at the end of each domain section as "Fixed silently."

The big realization from this pass: the L3 docs describe a clean v1.0.0 design target, while the current code is the pre-v1.0.0 implementation. Most divergences are not "the doc is wrong" but rather "the doc presumes a refactor that is part of v1.0.0 scope." The questions below are about which presumptions to keep.

Cross-cutting (applies to multiple domains)​

XC1. L2 component refactor — are we committing to it in v1.0.0?

The L3 docs presume the L2 design from #351: separate users / organization_users for membership, work_order_inputs for recipe snapshots, Documents component for file attachments, weighted-average cost rebuilds, etc. The current code has none of these as L2 components — it has direct table access spread across the routes.

  • A: Commit. v1.0.0 includes the L2 refactor as planned. The L3 docs become the spec.
  • B: Defer. Document the current direct-access shape; treat L2 as a future stage.

Recommend A. Without the L2 split, L3 doesn't really exist as a layer.

XC2. Cancelled status across PO / WO / SO — does v1.0.0 actually support cancellation, and what does it reverse?

The L3 docs all describe Cancelled as a terminal status that reverses open ORDER/DEMAND/ALLOCATE entries but preserves RECEIVE/CONSUME (real movements). The current code:

  • PO: has Cancelled in the manual-transition map, but the update path does NOT delete ORDER ledger entries when transitioning to Cancelled.

  • WO: has no Cancelled status in the lifecycle at all (transitions are Draft → Entered → Placed → In prod → Partial → Received → Completed).

  • SO: has Rejected, In-Dispute, Completed as terminal branches but the cancellation-as-rollback semantics are not implemented.

  • A: Build cancellation reversal as documented. Add the missing delete-ORDER logic to all three.

  • B: Drop cancellation reversal from the docs. Treat Cancelled as a label-only terminal state that doesn't move inventory.

XC3. Status name canonicalization — are the seed status names exactly the ones the docs use?

Mismatch examples found:

  • WO uses "In prod" in code, not "In Production" (which the docs use).
  • WO has "Completed" as a terminal state (alongside "Received"), not mentioned in docs.
  • PO automatic transitions (Partial, Received) match.
  • SO statuses (Received, Entered, Shipped, Invoiced, Paid, Rejected, In-Dispute, Completed) — need verification.

The status types are configurable per org (so an org could rename them), but the auto-transition + cascade code matches on names. What are the canonical seed names that the v1.0.0 docs should use?

XC4. Inventory ledger code generation — global vs per-tenant?

Materials ledger entries use code MIL-NNN and FG ledger entries use FIL-NNN. The current code generates these by scanning the ENTIRE table (across all orgs) for max-number, then incrementing. So codes are globally unique, not per-tenant. The docs imply per-tenant numbering.

  • A: Keep globally unique. Simpler counter (no per-org lock), and codes never collide across the catalog. Disadvantage: tenants see non-sequential numbers (a tenant might have MIL-001, MIL-007, MIL-012 etc.).
  • B: Make per-tenant. Reset numbering per org so each tenant sees clean sequences.

Same question applies to TFR-MI-NNN and TFR-FG-NNN transfer refs, and to PO numbers (PO-NNN), WO numbers (WO-NNN), SO numbers (SO-NNN).

XC5. Branding / per-org settings — is the organization_settings table part of v1.0.0?

Hardcoded per-org branding (legal name, address) is surfaced today through a lib/branding.ts registry that maps org name to hard-coded values. The L3 docs presume a runtime-editable organization_settings table.

  • A: Build organization_settings in v1.0.0. Per-org values become user-editable, branding registry is retired.
  • B: Keep hardcoded branding for v1.0.0. The L3 docs around W004 (Update org), W014 (Get org), W039 (Generate PO PDF) drop the settings layer.

Platform (W001–W019)​

P1. Sign-up / org-creation coupling. Today POST /api/auth/signup creates org + owner together because the schema requires users.org_id. With the L2 membership refactor (XC1=A) the docs are correct. Without it, W001 cannot create a user without also creating an org.

P2. Last-owner orphan-guard on W006 and W007. Docs include it; code does not. Recommend adding the rule.

P3. W008 idempotent re-invite. Doc says idempotent (returns existing pending), code returns HTTP 409 on duplicate. Pick one.

P4. W005 (Delete organization) — purge scope. Doc lists explicit per-domain sweep + GCS cleanup. Code does only DELETE FROM users + DELETE FROM organizations (presumably with FK CASCADE handling the rest). Pick one.

Fixed silently (Platform)​

  • W009 Resend invitation: code DOES extend expires_at by 7 days — doc updated.
  • W011 Accept invitation: documented the SELECT FOR UPDATE race-protection and the per-IP rate limit, removed the "run W001 inline" step.
  • W012 Decline invitation: corrected trigger context to authenticated route + invitation id; noted shared revoked_at column with revoke.
  • W013 Get current user: added updateLastLogin side-effect and the Cache-Control: no-store response header; documented X-Org-Id resolution.
  • W014 Get organization: dropped the settings merge step (no settings table today); noted as future-state.
  • W018 Look up by token: added rate-limit and 410 responses for consumed tokens.

Purchase Orders (W020–W041)​

PO1. PO cost fields — shippingCosts, setupCosts, costs not in the docs.

The PO header has shippingCosts and setupCosts fields plus a derived costs field that the backend keeps in sync (costs = sum(receipt_items.qty * unit_cost) + shipping + setup). The list and detail reads also expose expectedTotal (uses PO items' expected qty * unit_cost) and actualTotal (uses receipts). The doc treats PO costs as a single value derived from items only.

Should the docs describe the full cost model (header shipping + setup, expected vs actual rollup) or stick with the simplified view?

PO2. PO Cancelled reversal. See XC2.

PO3. PO delete does not purge ledger today. Doc says "delete every ledger entry tied to this PO + re-run cascade." Code only deletes po_items and the PO header (and relies on FK CASCADE for receipts/items). ORDER and RECEIVE ledger entries are orphaned with a now-stale ref = poNumber. Confirm: do we build the purge for v1.0.0?

PO4. W027 (Create receipt) cost-cascade scope — materials-only is broken for FG.

The cascade functions (cascadeCostsFromPO, cascadeDownstreamCosts) are hard-coded to materials. For materials POs, create-receipt path uses cascadeDownstreamCosts (skips MI rebuild because just inserted); update/delete paths use cascadeCostsFromPO (rebuilds MI from receipt_items). For FG POs, calling cascadeCostsFromPO would attempt to insert MI ledger entries with NULL material_id — a bug waiting to happen. The doc captures the materials-only branching as a business rule but doesn't flag the FG receipt path needing its own logic.

For v1.0.0: should FG PO receipts skip the cascade entirely (as documented), or should there be a parallel FG receipt cascade? Today FG PO receipts don't produce downstream cost dependencies, so skip seems right, but we should make this explicit in code.

PO5. PO receipt is NOT atomic with cost cascade today.

Docs say "atomic across the cascade" (W027 business rule 2). Actual code: the receipt INSERT + ledger INSERT runs in withTransaction; the recalcPurchaseOrderCosts, recalcPOStatusFromReceipts, and cascade calls run AFTER the transaction commits. So an interleaved reader can see the new receipt without the new cost rollup or status advance. Is this safe to assume the docs are the design intent and the code is a known gap to be closed in v1.0.0?

PO6. Status-advance only runs when current status is Placed / In Transit / Partial / Received.

So if a PO is in Planning and you create a receipt against it, the status does NOT advance. The doc implies advance is unconditional. Confirm: should advance work from any non-terminal status, or only from these four?

PO7. PO transitions to Placed from Planning write ORDER entries IF none exist (existence check via SELECT 1 LIMIT 1).

Doc says "insert them now: one per line via recordOrder, ref = poNumber." Same outcome but the existence check matters: re-transitioning Planning → Placed → Planning → Placed will not double-insert. Worth surfacing in the rule.

Fixed silently (Purchase Orders) — none yet, see Round 2 after PO design questions are answered.​

Work Orders (W042–W057)​

WO1. WO status names — code uses "In prod" not "In Production"; adds "Completed".

Canonical seed status names per code: Draft, Entered, Placed, In prod, Partial, Received, Completed. Docs say Draft → Placed | Cancelled etc. — both the names and the absence of Cancelled need reconciling. See XC2 and XC3.

WO2. WO writes DEMAND and ALLOCATE entries on the MATERIALS ledger.

This is a big one missing from the docs. Current code:

  • On WO transition to Entered or Placed: writes DEMAND entries on MI ledger for every material in every output line's BOM (using live BOM, not a snapshot). Same on FG ledger for input-SKU lines.
  • On transition to In prod or beyond: ensures DEMAND exists, then writes ALLOCATE.
  • ORDER entries on FG ledger for output SKUs (already documented).

My W042 / W043 docs only describe FG ORDER entries. The materials DEMAND / ALLOCATE flow is completely missing. Confirm: is this the intended v1.0.0 model?

WO3. Recipe snapshot does not exist; BOM is read live every time.

The L2 component design has work_order_inputs as a frozen snapshot. Current code has no such table — material requirements and cost rollups recompute from the live BOM on every WO read/update.

This is a real correctness question for v1.0.0: a BOM edit between WO creation and WO receipt today silently changes what the WO "should" consume. The snapshot table fixes this.

  • A: Build work_order_inputs in v1.0.0 as documented. Recipe is frozen at WO creation.
  • B: Keep live-BOM behavior. Document the consequence clearly (BOM edits affect in-flight WOs).

WO4. materialUnitCost is COMPUTED at WO creation, then frozen unless WO is re-saved with items.

Docs say "L3 computes materialUnitCost as Σ (bom_input.quantity × weighted_avg_unit_cost(input))" — correct. But the code uses computeMaterialUnitCost(client, item.skuId) which uses the LIVE materials ledger average. Then writes that value to work_order_items.material_unit_cost. Subsequent receipts on materials POs run cascadeCostsFromPO which RE-COMPUTES and RE-WRITES material_unit_cost for affected WO items.

So material_unit_cost is a snapshot that gets updated by the cascade. Doc treats it as set-once. Worth clarifying.

WO5. Multi-level BOMs — the cost cascade only handles material inputs.

The cascade SQL (cascadeCostsFromPO) walks bom_items WHERE sku_id = ? ... material_id IS NOT NULL (actually it doesn't filter by material_id IS NOT NULL — but iterates and reads bom.material_id). For BOM inputs that are SKUs (sub-assemblies), the cascade silently treats them as zero-cost. WO creation also has the same gap.

For v1.0.0: do BOMs support sub-assembly SKUs, and if so does the cost cascade need to recurse?

WO6. materialStatus derived field on WO list and detail.

Code computes a Material Status per WO (Insufficient / Incoming / In-Stock / Allocated / Consumed). My W052 and W053 docs don't mention this. Should this field be part of the L3 contract?

WO7. WO delete only deletes work_order_items + work_orders, orphans the ledger.

Same gap as PO3. Doc says "delete every materials ledger entry + every FG ledger entry for this WO". Code does neither.

Fixed silently (Work Orders) — pending Round 2 after WO design questions.​

Sales Orders (W058–W088) — pending second-pass review​

SO has its own ledger file (sales-orders-ledger.ts) plus the orders code itself. Findings so far from cross-domain scan:

  • Code has enrichOrdersWithFulfillmentStatus that derives a computed status from the FG ledger CONSUME totals. My W079 doc has this correctly.
  • No SO doc cancellation reversal logic (see XC2).
  • SO line items support price-only updates; quantity changes need ledger sync (DEMAND/ALLOCATE delete + re-insert) which the doc covers but the code may or may not.

SO1. Pending second-pass code review. I'll do a fuller pass on db/sales-orders.ts and db/sales-orders-ledger.ts after these cross-cutting and PO/WO questions land.

Inventory (W089–W102) — pending review​

The materials and FG inventory ledger files are 630 and 654 lines respectively, with rich event-type semantics (DEMAND, ALLOCATE, CONSUME, PRODUCE, RECEIVE, TRANSFER, ADJUST, DISPOSE). Per-event-type validations and indirect writes from PO/WO/SO are intertwined.

INV1. Transfer flow — quantity sign convention in code vs doc.

Doc says outbound is stored as -quantity, inbound as +quantity. Need to verify against the actual recordTransfer op. Pending pass.

INV2. Stock-protection on consumption / transfer — the docs flag "no stock guard in v1" repeatedly; confirm this is the intended state.

Master data (Customers, Products, BOM, Vendors, Materials, Locations, Contacts) — pending review​

These are mostly CRUD + in-use checks. Lower risk of design questions, but I want to verify:

  • Code-uniqueness rules (case-insensitive vs sensitive)
  • Soft-delete vs hard-delete semantics per entity (is setActive always available, or only for some?)
  • In-use check completeness (e.g., is broker in-use checked across SOs and customers as docs claim?)
  • BOM cycle detection (docs say "not implemented for v1, relies on data hygiene")

MD1. Pending second-pass review per domain.
