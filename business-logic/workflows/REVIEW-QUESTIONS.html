Round 2 open (new findings)​

Three substantive design questions surfaced during the second-pass review after Round 1 answers were locked. These do not block the Round 2 doc updates already applied but need resolution before implementation can start.

Q-R2-1. SO ledger reversal — hard delete vs. reverse entries?

The SO ledger code is explicitly append-only and idempotent (db/sales-orders-ledger.ts), with the comment: "Status regressions are rare and should be handled via explicit reverse entries, not by wiping history." Per XC2=A you committed to "build cancellation reversal." The cleanest interpretation given the append-only constraint is insert reverse entries (negative-quantity rows with event_type = 'REVERSE_DEMAND' / 'REVERSE_ALLOCATE' and the original source_id) rather than hard delete. PO and WO cancellation could follow the same pattern for consistency, or stay with hard delete.

  • A: Append-only reverse entries everywhere (PO, WO, SO). Adds two event types per ledger. Best audit trail.
  • B: Hard delete on PO and WO; reverse entries on SO (since the ledger is append-only by design). Inconsistent across domains but matches current code intent.
  • C: Hard delete everywhere. Simpler. Loses audit trail for cancellations.

I currently have W059 documented as reverse-entries. PO and WO docs still say hard-delete. They need to land on the same convention.

Q-R2-2. Inventory cost convention — FIFO or weighted-average?

Two cost conventions are in current code, used in different places:

  • FIFO for CONSUME / DISPOSE / TRANSFER / ALLOCATE stamping (getFifoAverageUnitCost consumes oldest RECEIVE/ADJUST layers first).
  • Weighted-average across all RECEIVE entries for the W027 cost cascade (rolling up to WO material_unit_cost).

For v1.0.0, do we:

  • A: Keep both. CONSUME-side stamping is FIFO; cascade-side rollup is weighted-average. The docs need to surface the distinction.
  • B: Unify on FIFO. The cascade re-pulls FIFO at recompute time.
  • C: Unify on weighted-average.

The fact that current code uses both suggests they serve different purposes; keeping both seems right but worth confirming.

Q-R2-3. Transfer model — single-row with to_location_id or paired entries?

The materials and FG ledger tables have a to_location_id column. Current code on TRANSFER inserts a single row with the source location_id, the destination to_location_id, the negative quantity, and the auto-generated TFR-MI-NNN / TFR-FG-NNN ref. The paired RECEIVE entry (with ref matching) marks completion at destination.

My W089/W090, W096/W097 docs describe the model as "outbound entry with quantity = -X at source, inbound entry with quantity = +X at destination, both sharing the ref" — which is close to the code but misses the to_location_id field. For v1.0.0:

  • A: Keep single-row TRANSFER with to_location_id plus paired RECEIVE on completion. Docs updated to reflect.
  • B: Switch to two paired entries (no to_location_id field). Simpler model, drops a column.

A is what the code does; B is what the docs almost describe. They're behaviorally identical for inventory math but different for storage and audit.
