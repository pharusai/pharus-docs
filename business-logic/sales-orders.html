Sales Orders

Workflows for sales orders, their line items, timeline notes, attached documents, and the three SO-side master-data tables (order channels, order status types, fulfillment status types). SOs are the demand side of finished goods — every line is a SKU the org has promised to deliver. On creation and through the fulfillment lifecycle, SO workflows write DEMAND / ALLOCATE / CONSUME entries to the FG ledger, mirroring how PO and WO workflows feed it.

Composes: SalesOrders, FinishedGoodsInventory, Customers, Products, Locations, Documents.

Status enums (seeded from order_status_types): Received → Entered → Shipped → Invoiced → Paid plus terminal branches (Rejected, In-Dispute, Completed). Fulfillment status (seeded from fulfillment_status_types): Pending → Partial → Fulfilled, derived but also editable.

Writes​

1. Create sales order​

Triggered from the Sales Orders page → "New SO". Records demand against finished-goods inventory.

Composes: SalesOrders, Customers, Locations, Products, FinishedGoodsInventory.

Steps:

  1. Generate the next SO number (SO-001, …).
  2. Verify the customer, fulfillment location, channel, and order/fulfillment statuses exist and are active.
  3. SalesOrders.createSo with header fields and initial statuses (default Received / Pending).
  4. For each line item: verify the SKU exists, then SalesOrders.addItem.
  5. For each line, write a DEMAND entry to the FG ledger via FinishedGoodsInventory.recordDemand — quantity, locationId = fulfillmentLocationId, ref = soNumber, unitCost left null (DEMAND is a quantity-only signal).

Returns: the new SO with hydrated items.

Business rules:

  • DEMAND entries appear at SO creation, before any inventory is allocated or shipped.
  • Brokers, MABD, and QBO id are optional metadata; they don't influence the ledger.

Errors:

  • NotFoundError — customer, location, channel, status, or SKU not found.
  • ValidationError — referenced status types not configured for this org.

2. Update sales order​

Triggered from Sales Order Detail.

Composes: SalesOrders, FinishedGoodsInventory.

Steps:

  1. SalesOrders.getSoById — load current state.
  2. If status changed, validate the transition (manual map enforced; see seeded transitions above).
  3. On status transitions that move inventory:
    • Entered: write ALLOCATE entries for each line via recordAllocation (one per line, ref = soNumber). DEMAND entries are kept — they remain as the SO's promise marker.
    • Shipped: write CONSUME entries via recordConsumption. Delete the ALLOCATE entries (their job is done). Stamp the CONSUME unitCost with the weighted-average FG unit cost at consume time.
    • Rejected / Cancelled-flavoured terminals: delete DEMAND and ALLOCATE entries for this SO. CONSUME entries — if any (partial ship before cancel) — stay.
  4. SalesOrders.updateSo.
  5. If line quantities haven't changed but the user has manually edited fulfillmentStatus, write it through directly; otherwise the workflow derives it from the FG ledger CONSUME totals (see §13).

Returns: the updated SO.

Business rules:

  • customerId is immutable after creation.
  • fulfillmentLocationId is editable only while in Received / Entered and propagates to any ALLOCATE entries that already exist (delete + re-insert at the new location).
  • CONSUME entries are at-cost-of-shipment; they are not re-priced if conversion costs change later. (Trailing-cost adjustments out of scope for v1.)

Errors:

  • NotFoundError, InvalidTransitionError, ValidationError.

3. Delete sales order​

Triggered from Sales Order Detail.

Composes: SalesOrders, FinishedGoodsInventory, Documents.

Steps:

  1. SalesOrders.getSoById — confirm.
  2. Documents.listByEntity('sales_order', soId) and Documents.delete for each — detaches files from the SO and removes them from GCS.
  3. Delete every FG ledger entry tied to this SO: listEntries({ refLike: soNumber }), then deleteEntry for each. This includes DEMAND, ALLOCATE, and CONSUME entries.
  4. SalesOrders.deleteSo — cascades to items and timeline notes.

Business rules:

  • Deleting an SO that has been shipped removes its CONSUME entries; the FG inventory goes "back up" by the consumed quantity. This is intentional — deleting an SO is a corrective action, not an end-of-life one. Users should mark the SO Completed rather than deleting once shipment has happened.

Errors:

  • NotFoundError.

4. Bulk-import sales orders​

Triggered from the Data page → SO import.

Composes: same as Create SO.

Steps:

  1. Parse the upload into { header, items[] } rows. Collect parse errors.
  2. Abort on any parse failure.
  3. Inside one withTransaction, run Create SO's steps 1–5 for each row.

Errors: ValidationError.

5. Add item to sales order​

Triggered from Sales Order Detail items section.

Composes: SalesOrders, Products, FinishedGoodsInventory.

Steps:

  1. SalesOrders.getSoById — confirm and read current status.
  2. Verify the SKU exists and is active.
  3. SalesOrders.addItem with quantity and unit price.
  4. Write a DEMAND entry for the new line. If the SO is past Entered, also write an ALLOCATE entry. If past Shipped — refuse the add; line items can't be added to shipped orders.

Errors:

  • NotFoundError, InvalidTransitionError.

6. Update sales order item​

Triggered from Sales Order Detail items section.

Composes: SalesOrders, FinishedGoodsInventory.

Steps:

  1. SalesOrders.getItemById — confirm and read parent SO.
  2. If the SO is Shipped or beyond, refuse — shipped items are immutable.
  3. SalesOrders.updateItem with patch.
  4. If quantity changed, delete and re-insert the DEMAND entry (and ALLOCATE, if past Entered) for this line to keep the ledger in sync.
  5. If SKU changed, treat as remove + add: delete all open ledger entries for the old line, write new DEMAND (+ ALLOCATE) for the new SKU.

Errors:

  • NotFoundError, InvalidTransitionError.

7. Remove item from sales order​

Triggered from Sales Order Detail items section.

Composes: SalesOrders, FinishedGoodsInventory.

Steps:

  1. SalesOrders.getItemById — confirm.
  2. If the parent SO is Shipped or beyond, refuse.
  3. Delete any FG ledger entries (DEMAND / ALLOCATE) tied to this line.
  4. SalesOrders.removeItem.

Errors:

  • NotFoundError, InvalidTransitionError.

Composes: SalesOrders.

10. Upload document to sales order​

Triggered from Sales Order Detail documents section.

Composes: SalesOrders, Documents.

Steps:

  1. SalesOrders.getSoById — confirm.
  2. Documents.create({ entityType: 'sales_order', entityId: soId, name, mimeType }, bytes) — uploads to GCS and inserts the row inside the transaction.

Returns: the new document.

Errors:

  • NotFoundError.

11. Delete document from sales order​

Triggered from Sales Order Detail documents section.

Composes: SalesOrders, Documents.

Steps:

  1. Documents.getById — confirm and verify it's attached to this SO.
  2. Documents.delete.

Errors:

  • NotFoundError, ValidationError — document not attached to this SO.

21. List sales orders​

  2. Batch-hydrate customers and channels onto each row.

22. Get sales order detail​

Triggered by clicking an SO. Returns the SO with a computed fulfillment status derived from the FG ledger.

Composes: SalesOrders, Customers, Locations, Products, FinishedGoodsInventory, Documents.

Steps:

  1. SalesOrders.getSoById.
  2. Load items, hydrate SKUs.
  3. For each line, sum CONSUME quantities from the FG ledger (listEntries({ refLike: soNumber, eventType: 'CONSUME' })); compare to expected to derive a computed fulfillment status (Pending / Partial / Fulfilled).
  4. If the computed status differs from the stored fulfillment status, both values are returned — the UI surfaces the computed one and keeps the stored value as the "user-set override" indicator.
  5. Load timeline notes and documents (Documents.listByEntity).

Returns: the merged hydrated view.

Notes:

  • The dual computed / stored fulfillment status is a deliberate v1 choice: the ledger is the source of truth, but allowing a manual override gives sales ops a release valve when reality diverges from the data. A future iteration may collapse the two into a derived-only field.
