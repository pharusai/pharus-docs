Stage A — Cross-layer review (L1–L4)

A consolidated pass over the four design layers as a whole, after each was drafted independently. This is the pre-implementation punch list — what to address before or during the build (Tasks 7–14).

Refs #346, #367. Layers under review:

  • L1 user actions — docs/api/user-actions/{entity}.md
  • L2 components — docs/components/{entity}.md
  • L3 workflows — docs/business-logic/workflows/{entity}/W###-*.md
  • L4 endpoints — docs/api/endpoints/{entity}/E###-*.md
  • Data — docs/data/{platform,org}/*.md

Headline​

The design is tight. 176 user actions across 13 domains map 1:1 to W### workflows and E### endpoints with consistent numbering and naming. No orphaned tables, no dead component operations, no naming divergences between W### and E### pairs, no inline TODO/TBD/FIXME markers anywhere in the docs.

The punch list below is short by design — these are the items where the cross-cutting pass actually surfaced something.

Gaps to close before implementation​

G1. PO and WO document attachments — data + L2 only, no L1/L3/L4​

  • org.documents.entity_type ENUM declares purchase_order and work_order as valid values (docs/data/org/documents.md).
  • data/org/purchase-orders.md and data/org/work-orders.md both document that attachments live in the polymorphic table.
  • L2 Documents component supports all three entity types uniformly.
  • But there are no user actions, workflows, or endpoints for uploading/deleting documents on a PO or WO. Only SO has them (W067/E067 upload, W068/E068 delete).

Decision owed: include PO/WO document upload/delete/list in v1, or drop the ENUM values from the data model until needed. If keeping, add 6 user actions + 6 W### + 6 E### (upload, delete, list × 2 entities).

G2. SalesOrders.syncLedger(soId) referenced by L3 but not defined on L2​

  • W058 step 5 and W059 step 5 both call SalesOrders.syncLedger(soId).
  • docs/components/sales-orders.md does not list this operation.
  • Likely either (a) an unlisted L2 op or (b) an L3-only helper that should be named accordingly. The workflows currently call it through the component namespace, which implies (a).

Decision owed: document syncLedger as a first-class L2 op (signature, idempotency contract, deduping key) — or rename it so it isn't mistaken for one.

G3. Reactivate action missing for several is_active entities​

  • Reactivate user action exists for: vendors, products, materials (3).
  • is_active exists in data model for: contacts, customers, locations, order_channels, plus the lookup tables (customer_types, customer_segments, brokers, material_types, sku_types, po_status_types, wo_status_types, order_status_types, fulfillment_status_types).
  • L2 exposes setCustomerActive, etc., but L1 surfaces only Delete.

Decision owed: either (a) add Reactivate actions for the missing entities (cheapest if all share the same pattern), or (b) drop is_active from entities that aren't meant to be reactivated by users (and let delete be hard). Mixed state today.

Decisions still owed (non-blocking but pre-implementation)​

D1. OpenAPI codegen toolchain​

docs/api/index.md commits to OpenAPI as the source of truth and to generating Zod + TS types into @pharus/api-contracts. Tool, OpenAPI version (3.0 vs 3.1), and CI regeneration step are not chosen. Needs to be settled before Task 11 (L4 implementation) starts so the contract package shape is stable.

D2. Migration plan detail​

Task 8 ("Database migration") commits to applying the new data model to develop-1.0.0 including data movement. No detailed migration ordering, backfill scripts, validation queries, or rollback strategy exist yet. With the new schema/namespace split (platform vs org) this is non-trivial.

D3. Frontend type consumption pattern​

Codegen produces types into @pharus/api-contracts. Pattern for the frontend (one-shot fetch + typed client wrapper vs. per-endpoint hook generation) is unspecified. Affects Task 12.

Items consciously deferred — verified, not action items​

These showed up in the search and were checked. They are correctly out of scope for v1 and tracked elsewhere:

  • Audit log — #358
  • Shared L3 logic extraction — #360
  • Reads inside withTransaction — #361
  • Typed error → API code mapping — #362
  • Idempotency keys — #363
  • Background workers / cron / queues — explicitly v1-out-of-scope (business-logic/index.md)
  • BOM cycle detection — v1 relies on data hygiene
  • Cost cascade — inlined into W027/W042/W046 by design, not extracted

Areas verified clean​

  • Layer pairing: every W### has its matching E### with the same slug; numbering is contiguous within each entity range; no duplicates.
  • Tenant context: ambient via SET LOCAL app.org_id on the connection, with belt-and-suspenders explicit WHERE org_id = $1 in L2 SQL. Consistently applied across all org-scoped components. Platform component is deliberately tenant-unaware.
  • Anthem-specific data: lives in org.organization_settings (singleton per org), read by L2. No hardcoded branding in L3. PDF generation soft-renders with X-Pharus-Warning: branding_incomplete when fields are missing.
  • Error envelope, pagination, versioning: all decided in api/index.md.
  • Platform vs org split: clean. platform.* for identity/membership/invitations; org.* for everything tenant-scoped. organizations row carries identity only; branding/legal moved to org.organization_settings.
  • Inventory ledger pattern: append-only with reversal entries; getSummary nets pairs on read. Consistent across materials and finished-goods.
  • Polymorphic documents and contacts: entity_type ENUM is the source of truth; no DB-level FK on entity_id, application-enforced cleanup is documented.
