L2 — Design decisions

Cross-cutting choices that shape every per-component page. Locked here so the per-component docs don't relitigate them.

Three decisions land before per-component pages get drafted:

  1. Component granularity — which entities become their own component vs. group under a larger one.
  2. Tenant context — how org_id flows into every L2 call.
  3. Connection handling — what type L2 ops accept, who owns transactions, and how the request boundary acquires conns.

All three are locked below.

Principles (recap from L2 overview)​

  • One component per domain. Thin DB-access API. No constraints, no cross-domain calls, no business rules. Constraints belong in L3.
  • Each operation accepts a conn parameter — no global pool, no hidden state.
  • Stateless. In-process today, separable later if needed.
  • Components own their tables. A table is owned by exactly one component; no other component reads or writes it directly.

Decision 1 — Component granularity​

Rule of thumb: one component per user-action domain (the pages under User Actions). Pull a separate component out only when its table cluster is shared by multiple domains or has its own lifecycle.

What is not its own component​

  • Status types (PO / WO / order / fulfillment). Not tables — Postgres ENUMs on the row. No CRUD operations possible; the existing "create/update/delete status type" user actions become no-ops in L2 and are flagged for the implementation phase to drop from the API surface.
  • WO inputs snapshot. Tied to WO lifecycle. Owned by WorkOrders.
  • Receipt items (po_receipt_items, wo_receipt_items). Lifetime is bound to their parent receipt; owned by PurchaseOrders and WorkOrders respectively.
  • organization_users. Membership rows. Owned by Users (identity + membership move together).

Cross-domain reads — how they work​

Components don't call other components. When a workflow needs data from two domains (e.g., SO detail with customer name), L3 calls both L2 components and joins in the workflow. L2 stays pure DB-access for its owned tables.

Exception worth flagging: the entity_contacts and documents polymorphic linkers expose lookups by (entity_type, entity_id). Callers from any domain pass their entity ID in. The component never resolves it back to the source table — that's the workflow's job.

Decision 2 — Tenant context​

Locked: Option B1 — session GUC carried by the connection. No RLS in Stage A.

The request boundary sets SET LOCAL app.org_id = $1 on the conn before passing it down. L2 component SQL reads the tenant via current_setting('app.org_id')::uuid (or equivalent) and still carries an explicit WHERE org_id = $1 clause — application-side filter is the contract, not RLS.

L2 signatures look like:

purchaseOrders.list(conn, { status: 'planning' });
// conn was prepared upstream with app.org_id set

No orgContext parameter; no policy layer.

Why B1 and not A or B2:

  • Not A (explicit orgContext) — would add a redundant parameter to every L2 op (~18 components × N ops) and would have to be ripped out at physical-split time anyway. Clean signatures + zero migration churn outweigh the grep-ability gain.
  • Not B2 (RLS) — defense-in-depth is real, but the operational cost (RLS policies move with every schema change) outweighs the win during Stage A. RLS is a lever we can pull later without changing application code shape: adding policies is a strict tightening, not a rewrite.

Options considered​

Option A — explicit orgContext parameter​

Option A — explicit orgContext parameter​

purchaseOrders.list(conn, orgContext, { status: 'planning' });
//                       ^^^^^^^^^^

orgContext is { orgId: string } (or richer if we need user/role inside L2 later, though Stage A says no).

Pros:

  • Visible at every call site. Easy to grep for missing orgContext. Easy to spot in code review.
  • Component implementations are pure functions: same inputs → same SQL. No reliance on connection state.
  • Trivial to test — pass a fixture orgContext.

Cons:

  • Every signature carries it. ~18 components × N operations = a lot of mechanical parameter passing.
  • Future per-tenant-DB migration: the orgId parameter becomes redundant (one tenant per DB) and has to be removed from every signature.

Option B — carried by the connection​

The conn enters L2 already scoped (e.g., a session GUC app.org_id is set, or search_path is narrowed). Component code reads it from the conn or uses a SQL pattern that picks it up implicitly.

purchaseOrders.list(conn, { status: 'planning' });
// conn was prepared upstream with org context set

Two flavors worth distinguishing:

  • B1: session variable — SET LOCAL app.org_id = $1 at the start of each request/transaction. Component SQL reads current_setting('app.org_id')::uuid where it needs the filter.
  • B2: RLS on org_id — policies on every tenant table use the same GUC to enforce org_id = current_setting('app.org_id'). Component SQL drops the WHERE org_id = $1 clause entirely; the policy enforces it.

Pros:

  • Clean signatures. Domain ops describe domain inputs only.
  • Easier physical-split migration: callers stop setting the GUC, queries already don't reference org_id. No L2 signatures change.
  • B2 in particular gives defense-in-depth: a missed WHERE clause can't leak across tenants.

Cons:

  • Component correctness depends on caller discipline (or a guarded conn factory). Forgetting to set the GUC = silent cross-tenant query.
  • Less greppable. "Which component reads org?" → all of them, implicitly.
  • Tests need a conn with the GUC set; fixtures get a bit heavier.
  • B2 adds policy-management surface (RLS policies must move with every schema change). Worth it only if we're committed to RLS as defense-in-depth.

Decision 3 — Connection handling​

L2 components are stateless DB-access modules. They don't import a pool, don't open transactions, and don't decide which conn they get. The request boundary owns all three.

What L2 accepts​

Every L2 op accepts a Queryable — a tiny interface, not a pg type:

interface Queryable {
  query<T extends QueryResultRow = QueryResultRow>(
    sql: string,
    params?: unknown[],
  ): Promise<QueryResult<T>>;
}

// L2 op shape
async function listPurchaseOrders(
  db: Queryable,
  filters: { status?: PoStatus },
): Promise<PurchaseOrder[]> { /* ... */ }

Why Queryable and not PoolClient:

  • Tests pass a fake ({ query: async () => ({ rows: [...] }) }) — no need to stand up a real pg connection.
  • No pg lock-in inside L2. If we ever swap drivers (e.g. postgres.js), L2 doesn't change.
  • A PoolClient, a Pool, or a Client all satisfy Queryable. L2 doesn't care which it got.

Justification is testability + driver independence, not the future per-tenant-DB migration — routing happens at the boundary, not in the L2 type.

Who opens transactions​

L2 never calls BEGIN, COMMIT, or ROLLBACK. L3 owns the unit of work. If a workflow needs PO insert + ledger insert to commit together, L3 wraps both component calls in withTransaction and passes the resulting conn into each.

Two helpers at the request boundary​

The request boundary (Express handler → L3 workflow entry) acquires a conn from the pool via one of two helpers. Both apply SET LOCAL app.org_id = $1 so the tenant context is in place before any L2 SQL runs.

// Reads — no transaction, conn returned on completion.
async function withConnection<T>(
  pool: Pool,
  orgId: string,
  fn: (conn: PoolClient) => Promise<T>,
): Promise<T> {
  const conn = await pool.connect();
  try {
    await conn.query('SET LOCAL app.org_id = $1', [orgId]);
    return await fn(conn);
  } finally {
    conn.release();
  }
}

// Writes — wrapped in BEGIN/COMMIT, rolls back on throw.
async function withTransaction<T>(
  pool: Pool,
  orgId: string,
  fn: (conn: PoolClient) => Promise<T>,
): Promise<T> {
  const conn = await pool.connect();
  try {
    await conn.query('BEGIN');
    await conn.query('SET LOCAL app.org_id = $1', [orgId]);
    const result = await fn(conn);
    await conn.query('COMMIT');
    return result;
  } catch (err) {
    await conn.query('ROLLBACK');
    throw err;
  } finally {
    conn.release();
  }
}

Two helpers, not one — reads are the majority of ops, and a useless BEGIN/COMMIT on every list query adds noise without benefit. SET LOCAL is safe in both: in withConnection it's scoped to the implicit single-statement transaction pg uses for each query() call when no explicit transaction is open... so the GUC has to be set on every checkout. (This is a real quirk worth flagging in the implementation phase; the helper hides it from callers.)

What this means for L2 SQL​

Every L2 query that touches a tenant table carries WHERE org_id = $1 (or whatever shape — composite keys, joins). The app.org_id GUC is set, but the filter stays explicit. RLS is a lever for later.

-- L2 SQL inside listPurchaseOrders:
SELECT * FROM org.purchase_orders
WHERE org_id = current_setting('app.org_id')::uuid
  AND ($1::po_status IS NULL OR status = $1)
ORDER BY order_date DESC;

(Exact shape — current_setting(...) inline vs. passing orgId as a bound parameter — is an implementation choice. Either reads the GUC; either works.)
