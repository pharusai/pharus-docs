Platform / Org Split (draft)

Working draft for #350. Not a conclusion — a starting point for a deeper pass.

Scope​

Design the logical separation between platform data (users, orgs, auth, membership) and org data (tenant-scoped) inside the same Postgres database, in a way that becomes a clean physical split later (one platform DB + one DB per organization) without rewriting the application.

Out of scope today: physical multi-DB. Same instance, same database. Schemas (or another logical mechanism) only.

Proposed mechanism (to confirm)​

Use Postgres schemas as the boundary:

  • platform.* — tenant catalog and identity. Survives unchanged into a future platform DB.
  • org.* — tenant-scoped tables. In a future world, each tenant gets its own DB containing only the org.* schema (tenancy moves from the org_id column to the DB boundary).

Why schemas:

  • Zero application impact today: configure search_path per connection (SET search_path TO org, platform).
  • Names stay unqualified in queries.
  • Cross-schema FKs work natively (e.g., org.purchase_orders.org_id → platform.organizations.id).
  • The boundary is enforceable per role: a future "tenant role" can be granted access only to org.*.
  • Migration to physical split = move each schema into a new DB, no application rewrites.

Alternatives we'd reject:

  • One DB now, separate by prefix only (platform_users, org_purchase_orders) — no enforcement, harder to split later.
  • Separate databases now — physical multi-DB is explicitly out of scope.
  • Row-level security on org_id — solves a different problem (defense-in-depth), not the platform/org split.

Open questions (answer tomorrow)​

  1. users cardinality. Today users.org_id is NOT NULL — a user belongs to exactly one org. Standard SaaS shape is a separate organization_users (or memberships) bridge so one identity can join many orgs. Do we make this change now (clean foundation, more work) or defer (single-org membership, risk of rewrite later)?
  2. user_invitations placement. Has both org_id and invited_by (user). Logically it's the inter-tenant flow, so platform feels right. But it's only ever read by one org at a time. Platform or org?
  3. organizations shape. Today it stores name, slug, and branding / billing address fields. The identity row (id, slug, is_active) is clearly platform. Branding & billing address feel like "org settings" and could live in org.organization_settings. Worth splitting now or keep flat?
  4. org_id column on tenant tables. Today every org.* table will still need org_id (we're sharing one DB). In the physical-split future this column becomes redundant. Keep it everywhere now and plan to drop at split-time, or design org.* without it now and rely on schema-per-tenant + search_path? Trade-off: keeping org_id is safer today (defense-in-depth, easier debugging), but it's dead weight after the split.
  5. contacts / contact_methods / entity_contacts placement. Org-scoped today. Could one day be a platform-level shared pool (e.g., a vendor known to multiple orgs is the same contact). Keep org-scoped for v1, or design for shared now?
  6. materials vs skus (called out in issue body). Are they fundamentally different entities, or one table with a discriminator? Affects BOM modeling.
  7. customers vs vendors (called out in issue body). Should they merge into a unified contacts-style "external party" entity with role flags? Or stay split because their downstream use (POs vs SOs) is different?
  8. Status type tables. Per-org configurable today. Stay in org.*, or move to platform.* with a per-org override table? Most ERPs treat workflow statuses as system-defined with optional org tweaks.
  9. fulfillment_locations. Pure org master data — should be org.*. But used as ship-to / work-site / stock location across PO, WO, SO, and inventory. Naming-wise, "fulfillment_locations" leaks the SO bias. Rename while we're restructuring? (locations?)

What lands in this section when the questions are answered​

  • A finalized table-by-table classification.
  • The mechanism choice (schemas + search_path, almost certainly) with concrete DDL.
  • Per-question decisions with brief rationale.
  • The migration sketch from today's flat schema to the split layout — concrete enough to write the SQL migrations against.
