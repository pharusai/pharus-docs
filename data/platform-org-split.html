Platform / Org Split (draft)

Working draft for #350. Not a conclusion — a starting point for a deeper pass.

Scope​

Design the logical separation between platform data (users, orgs, auth, membership) and org data (tenant-scoped) inside the same Postgres database, in a way that becomes a clean physical split later (one platform DB + one DB per organization) without rewriting the application.

Out of scope today: physical multi-DB. Same instance, same database. Schemas (or another logical mechanism) only.

Proposed mechanism (to confirm)​

Use Postgres schemas as the boundary:

  • platform.* — tenant catalog and identity. Survives unchanged into a future platform DB.
  • org.* — tenant-scoped tables. In a future world, each tenant gets its own DB containing only the org.* schema (tenancy moves from the org_id column to the DB boundary).

Why schemas:

  • Zero application impact today: configure search_path per connection (SET search_path TO org, platform).
  • Names stay unqualified in queries.
  • Cross-schema FKs work natively (e.g., org.purchase_orders.org_id → platform.organizations.id).
  • The boundary is enforceable per role: a future "tenant role" can be granted access only to org.*.
  • Migration to physical split = move each schema into a new DB, no application rewrites.

Alternatives we'd reject:

  • One DB now, separate by prefix only (platform_users, org_purchase_orders) — no enforcement, harder to split later.
  • Separate databases now — physical multi-DB is explicitly out of scope.
  • Row-level security on org_id — solves a different problem (defense-in-depth), not the platform/org split.

Questions & decisions​

  1. users cardinality — identity vs membership shape. Today users stores one row per (firebase_uid, org_id) pair — multi-org works (org-switching joins on firebase_uid) but identity fields (email, display_name, last_login_at, is_active) are duplicated across rows, and users.id is semantically a per-membership PK while looking like an identity ID. References from other tables (e.g., user_invitations.invited_by) end up pointing at memberships, not people.

    Decision: split into identity + membership.

    • platform.users(id, firebase_uid UNIQUE, email, display_name, last_login_at, is_active) — one row per person.
    • platform.organization_users(id, user_id, org_id, role, joined_at, is_active) — one row per (person, org). role moves here.
    • One-shot migration: collapse duplicate users rows by firebase_uid, populate memberships, drop users.org_id and users.role. References from other tables decide case-by-case whether they point at the identity (users.id) or the membership (organization_users.id).

  2. user_invitations placement. Has both org_id (which org invited) and invited_by (which user invited). The "List my pending invitations" flow is unambiguously cross-tenant, so the table can't sit in any single org's schema in a future physical-split world.

    Decision: platform.user_invitations. invited_by → platform.users.id, org_id → platform.organizations.id. Per-org listing is a WHERE org_id = ? filter; cross-user listing is a WHERE email = ? filter. Both natural in shared-DB and physical-split worlds.

  3. organizations shape — identity vs settings. Today flat in one table; mixes catalog identity (id, slug, is_active) with per-tenant operational data (branding, billing address, legal name, etc.). Keeping it flat leaks tenant-scoped data into the future platform DB.

    Decision: split.

    • platform.organizations(id, name, slug, is_active, created_at, updated_at) — minimal catalog row. name stays platform-side because cross-tenant flows need it (My Organizations list, invitation acceptance UI).
    • org.organization_settings — one row per org schema. Holds legal name, address, branding (colors, logo), billing fields, anything else org-configurable.

  4. org_id column on tenant tables — keep or drop, and via what mechanism? Three shapes considered: (A) one shared org schema with org_id everywhere; (B) schema-per-tenant (org_acme.*, org_globex.*) and no org_id; (C) one shared org schema with org_id everywhere — same as A, but the org.* namespace is the platform/org boundary.

    Decision: C — middle ground. Keep one table per entity in a single org schema. org_id stays on every tenant table for shared-DB tenancy and defense-in-depth. The org.* namespace makes the platform/org boundary real today (search_path, role grants). Physical-split later = move the org schema into per-tenant DBs and drop org_id columns + the per-tenant unique-constraint migration. Application code is largely unchanged either way.

  5. contacts / contact_methods / entity_contacts placement. A shared platform pool would introduce immediate privacy obligations (one tenant could read another tenant's contacts) and an identity-resolution problem we don't currently have, all for a pretty rare cross-tenant overlap.

    Decision: org-scoped (org.contacts, org.contact_methods, org.entity_contacts). Each tenant's contacts stay private to that tenant. Survives physical split trivially.

  6. materials vs skus (called out in issue body). Different attributes (pricing, items-per-unit, sellability) and different lifecycle (materials are bought, SKUs are sold). The user-facing model in the actions catalog also keeps them separate (Materials page vs Products page, Materials Inventory vs FG Inventory).

    Decision: keep separate (org.materials, org.skus). Accept the cost of polymorphism on bom_items (either input_material_id or input_sku_id, with a CHECK constraint enforcing exactly one). The collapse can be done later if pressure grows; the un-collapse is far harder.

  7. customers vs vendors (called out in issue body). Asymmetric in this product: customers have a much richer model (types, segments, brokers, hierarchy, currency, QBO ID), vendors are flat. Sales-side and purchase-side workflows attach different concepts. The user-actions catalog treats them as distinct domains. No real-world overlap case requested today.

    Decision: keep separate (org.customers, org.vendors). If a customer-that's-also-a-vendor case ever materializes, solve it with a soft link (e.g., vendors.customer_id nullable FK) rather than restructuring into a unified business-parties model.

  8. Status type tables — platform-level or org-scoped? Schema and routes are configurable today, but the Settings UI for editing status types was hidden (#334) — product reality is "system-defined." L3 workflows will eventually need to reference specific statuses (e.g., "transition to In Transit triggers ledger ORDER entry"), which is impossible if every tenant curates their own list.

    Decision: platform-level. Move po_status_types, wo_status_types, order_status_types, fulfillment_status_types into platform.*. One canonical list per family, identical for every tenant. If per-org overrides ever become a real product need, layer them in later as org.<x>_status_type_overrides — additive, cheap. The reverse (start configurable, retrofit a canonical list across diverged tenant lists) is migration pain.

    Side effect: the user-actions catalog still lists Create / Update / Delete <x> status type as writes on each domain page. Those are stale in the same way the backfill entries were — clean them up in a follow-up pass to the catalog.

  9. fulfillment_locations naming. Used as PO ship-to, WO work site, SO fulfillment location, and inventory stock bin — the "fulfillment" prefix leaks a sales-side bias the entity doesn't have. The user-actions page already calls it Locations.

    Decision: rename to org.locations. FK columns rename fulfillment_location_id → location_id everywhere. Mechanical change, piggybacks on the schema-namespace migration we're doing anyway. The honest name aligns the schema with user-facing language.
