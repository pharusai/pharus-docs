Decisions

The 9 design questions walked during the L1 design pass, with the call and the reasoning behind it. Kept separate from the schema reference so future readers can answer "why is it like this?" without scrolling through DDL.

Q1 — users shape — identity vs membership

Today: users stores one row per (firebase_uid, org_id) pair. Multi-org works (org-switching joins on firebase_uid) but identity fields are duplicated per org, and users.id is semantically a per-membership PK while looking like an identity ID.

Decision: split into identity + membership.

  • platform.users(id, firebase_uid UNIQUE, email, display_name, last_login_at, is_active) — one row per person.
  • platform.organization_users(id, user_id, org_id, role, joined_at, is_active) — one row per (person, org). role moves here.

Why: the row-per-membership pattern works for switching orgs but quietly breaks identity invariants (one person, one profile) and makes references from other tables semantically muddy. Doing it now is one migration; doing it later means refactoring everywhere that's grown to assume users.id is an identity ID.

Q2 — user_invitations placement

Today: user_invitations(org_id, invited_by → users.id, email, role, token, ...).

Decision: platform.user_invitations. invited_by → platform.users.id, org_id → platform.organizations.id.

Why: the "List my pending invitations" flow is unambiguously cross-tenant — by definition a user can be invited to orgs they don't currently belong to. That makes it impossible to put this table in any single org's schema in a future physical-split world. Per-org listing is just a WHERE org_id = ? filter.

Q3 — organizations shape — identity vs settings

Today: flat organizations table mixing tenant catalog identity (id, slug, is_active) with per-tenant operational data (branding, billing address, legal name).

Decision: split.

  • platform.organizations(id, name, slug, is_active, created_at, updated_at) — minimal catalog row.
  • org.organization_settings — one row per org schema. Holds legal name, address, branding (colors, logo), billing fields, anything else org-configurable.

Why: keeping operational data on the platform table leaks tenant-scoped data into the future platform DB. name stays platform-side because cross-tenant flows need it (My Organizations list, invitation acceptance UI).

Q4 — org_id column on tenant tables

Considered:

  • (A) one shared org schema with org_id everywhere.
  • (B) schema-per-tenant (org_acme.*, org_globex.*) and no org_id.
  • (C) one shared org schema with org_id everywhere — same as A, but the org.* namespace is the platform/org boundary.

Decision: C — middle ground.

Why: A misses the boundary. B is heavy (DDL runs N times per migration, observability fragments) and we don't need its isolation in the shared-DB phase. C makes the boundary real today (search_path, role grants) without paying schema-per-tenant costs. Physical split later = move the org schema into per-tenant DBs and drop org_id columns + the per-tenant unique-constraint migration. Application code is largely unchanged either way.

Q5 — Contacts placement

Considered: keep org-scoped, or promote to a shared platform.contacts pool that multiple orgs can reference.

Decision: org-scoped (org.contacts, org.contact_methods, org.entity_contacts).

Why: a shared pool would introduce immediate privacy obligations (one tenant could read another's contacts) and an identity-resolution problem we don't currently have, all for a pretty rare cross-tenant overlap. Each tenant's contacts stay private. Survives physical split trivially.

Q6 — materials vs skus

Considered: keep separate; or unify into one org.items with a kind discriminator; or hybrid (separate tables behind a thin abstraction).

Decision: keep separate (org.materials, org.skus). Accept the cost of polymorphism on bom_items (input_material_id XOR input_sku_id, with a CHECK enforcing exactly one).

Why: materials and SKUs have meaningfully different attributes (pricing, items-per-unit, sellability) and different lifecycle (materials are bought, SKUs are sold). The user-facing model in the actions catalog also keeps them separate (Materials page vs Products page, Materials Inventory vs FG Inventory). The collapse can be done later if pressure grows; the un-collapse is far harder.

Q7 — customers vs vendors

Considered: keep separate; or unify into a business_parties table with role flags + role-specific extension tables.

Decision: keep separate (org.customers, org.vendors).

Why: asymmetric in this product. Customers have a much richer model (types, segments, brokers, hierarchy, currency, QBO ID); vendors are flat. Sales-side and purchase-side workflows attach different concepts. The user-actions catalog treats them as distinct domains. No real-world overlap case requested today. If a customer-that's-also-a-vendor case ever materializes, solve it with a soft link (vendors.customer_id nullable FK) rather than restructuring into a unified business-parties model.

Q8 — Status types

Today: four org-scoped tables (po_status_types, wo_status_types, order_status_types, fulfillment_status_types), each with (org_id, name, sort_order, ...). Schema and routes are configurable, but the Settings UI for editing status types was hidden in #334 — product reality is "system-defined."

First-pass decision (revised below): move all four into platform.* as canonical tables. The reasoning held — system-defined, identical per tenant — but the shape (table-with-FK) is heavier than what's actually needed.

Decision: replace with Postgres ENUM types in the org schema.

  • org.po_status, org.wo_status, org.order_status, org.fulfillment_status — one ENUM per workflow.
  • The transactional table carries the value directly: purchase_orders.status po_status NOT NULL, work_orders.status wo_status NOT NULL, sales_orders.order_status order_status NOT NULL, sales_orders.fulfillment_status fulfillment_status NOT NULL.
  • Display attributes (background color, text color, sort order) live in the application layer as a constant map. They're UI config, not data.
  • No status type tables. No cross-schema FKs for status. The only cross-schema reference left in the design is org_id.

Why:

  • The codebase already uses Postgres ENUMs for analogous "system-defined, identical per tenant" lists — see materials_inventory_event_type, finished_goods_inventory_event_type. Consistency.
  • L3 workflow code references statuses by stable name ('In Transit'). An ENUM expresses that contract at the type level; a table requires a name lookup at runtime.
  • Adding a status becomes a deliberate migration (ALTER TYPE ... ADD VALUE) rather than a runtime config knob — which matches how product-side decisions about workflow shape actually happen.
  • Drops 4 tables, 5 cross-schema FKs, and a "status types" page in the docs.

Where the ENUM lives. In org.* (alongside its consumer tables) rather than platform.*. The values are identical for every tenant, but the type is consumed only by org tables, and at physical-split time each tenant DB will have its own copy of the ENUM definition. No platform DB involvement needed.

Side effect: the user-actions catalog still lists Create / Update / Delete <x> status type as writes on each domain page. Those are stale in the same way the backfill entries were. Cleanup is a follow-up pass on the catalog, not part of this design.

Q9 — fulfillment_locations naming

Today: fulfillment_locations is used as PO ship-to, WO work site, SO fulfillment location, and inventory stock bin — the "fulfillment" prefix leaks a sales-side bias the entity doesn't have. The user-actions page already calls it Locations.

Decision: rename to org.locations. FK columns renamed fulfillment_location_id → location_id everywhere; work_site_id keeps its semantic name on work_orders.

Why: mechanical rename, piggybacks on the schema-namespace migration we're doing anyway. The honest name aligns the schema with user-facing language.
