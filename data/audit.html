Schema audit

Findings from a deep review of the current schema (database/schema.sql + migrations 040-044). Each item is something to address in the L1 design before implementation. Walked one by one; decisions land inline.

Items already resolved by the L1 design pass (Q1-Q9) aren't relisted here — see Decisions.

Findings are grouped by severity:

  • Critical (A1-A6) — data integrity / real risk.
  • Inconsistencies (A7-A20) — cleanup, no architectural change.
  • Improvements (A21-A29) — nice-to-haves.

Critical​

A1 — Default org_id placeholder

Every business table has org_id UUID NOT NULL DEFAULT '00000000-0000-0000-0000-000000000001' — the seeded Anthem UUID. Any insert that forgets to pass org_id silently writes to Anthem's tenancy. In a multi-tenant world this is a data-corruption hazard. The default should be removed (NOT NULL alone, no default), forcing every insert to be explicit.

Proposal: Drop the DEFAULT everywhere. Keep NOT NULL. Every insert must pass org_id explicitly — bugs surface at insert time instead of misrouting silently.

Decision: open

A2 — Sales order cost columns nullable with default 0

sales_orders.fulfillment_costs, freight_costs, promo_costs, other_costs, broker_fees are declared NUMERIC(18,6) DEFAULT 0 — no NOT NULL, no CHECK >= 0. So a column can be 0 or NULL (both mean "no cost"), and there's no protection against negative values. Compare with inventory_cost and order_value on the same table, which have both. Make all the cost columns NOT NULL DEFAULT 0 CHECK (... >= 0) for consistency and integrity.

Proposal: Make all five NOT NULL DEFAULT 0 CHECK (... >= 0) so they match inventory_cost and order_value. NULL stops being a synonym for 0; negatives become impossible.

Decision: open

A3 — No parent-child org_id consistency check

Child tables duplicate org_id from their parent (po_items.org_id alongside purchase_orders.org_id, etc.). There's no constraint that they match — a row could have purchase_orders.org_id = X and po_items.purchase_order_id pointing at a PO with org_id = Y. Application-enforced today.

Two viable shapes:

  • Accept the risk and document it as application-enforced.
  • Enforce via composite FK: (purchase_order_id, org_id) REFERENCES purchase_orders(id, org_id) — requires UNIQUE(id, org_id) on parents.

Proposal: Accept as application-enforced and document the rule. Composite FKs touching every parent/child pair is heavy for a risk that's already low (the application sets org_id once at the request boundary).

Decision: open

A4 — updated_at without an auto-update trigger

Some tables declare updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW() but have no BEFORE UPDATE trigger to bump it. Affects materials, work_orders, order_status_types, fulfillment_status_types. The column will silently lie (forever showing the original created_at value). Either add the trigger or drop the column.

Proposal: Add the trigger on materials and work_orders. The two status type tables disappear under Q8.

Decision: open

A5 — role columns have no CHECK constraint

users.role VARCHAR(50) NOT NULL DEFAULT 'member' and user_invitations.role VARCHAR(50) NOT NULL DEFAULT 'member' — the application says role ∈ {owner, admin, member, viewer} but the DB allows any string. A typo or bug can write 'memebr' and not be caught.

Options: CHECK constraint with the four values, or a Postgres ENUM (user_role or org_role).

Proposal: Postgres ENUM platform.org_role with values owner, admin, member, viewer. Lives next to its consumers (organization_users.role per Q1, user_invitations.role). Same pattern as Q8.

Decision: open

A6 — Ledger source_type / source_id not tied together

materials_inventory_ledger and finished_goods_inventory_ledger declare source_type TEXT and source_id UUID as separately nullable. Should be either both-null (manual entry) or both-set (originating row pointer). As written, you can have source_type='po_receipt' with source_id IS NULL, breaking the idempotency-key invariant.

Fix: add CHECK ((source_type IS NULL AND source_id IS NULL) OR (source_type IS NOT NULL AND source_id IS NOT NULL)).

Proposal: Add the CHECK to both ledger tables. Tiny constraint, enforces the invariant at write time.

Decision: open

Inconsistencies​

A7 — MABD is uppercase

sales_orders.MABD DATE NOT NULL — the only uppercase column name in the entire schema. Postgres folds it to lowercase, but it's confusing. Rename to mabd or, better, must_arrive_by_date.

Proposal: Rename to must_arrive_by_date. More verbose but matches snake_case convention and is self-explanatory.

Decision: open

A8 — qbo_id size mismatch

customers.qbo_id VARCHAR(50) vs sales_orders.qbo_id VARCHAR(100). Pick one (probably 100 — QBO IDs aren't huge but 50 is the smaller risk).

Proposal: Standardize on VARCHAR(100) everywhere qbo_id appears. customers.qbo_id gets enlarged.

Decision: open

A9 — Status type name size mismatch

po_status_types.name VARCHAR(50) and wo_status_types.name VARCHAR(50) vs order_status_types.name VARCHAR(100) and fulfillment_status_types.name VARCHAR(100). Becomes moot once Q8 (revised) replaces these tables with ENUMs, but until then, inconsistent.

Proposal: No action — Q8 removes all four tables. Mark resolved by Q8.

Decision: open

A10 — wo_status_types lacks updated_at

The four status type tables are siblings, but order_status_types and fulfillment_status_types have updated_at, while po_status_types and wo_status_types don't. Becomes moot once Q8 replaces them with ENUMs.

Proposal: No action — Q8 removes all four tables. Mark resolved by Q8.

Decision: open

A11 — vendors.notes exists; customers.notes doesn't

Both are external parties with similar shape; one carries free-form notes, the other doesn't. Decide whether customers should also have notes, or remove from vendors for symmetry.

Proposal: Add notes TEXT to customers. Free-form notes are useful on any party; aligning up beats aligning down.

Decision: open

A12 — updated_at coverage is uneven

customers, vendors, skus, purchase_orders, po_receipts are editable entities with no updated_at column at all. Every UPDATE silently doesn't get tracked. Either add updated_at (with trigger) consistently across editable entities, or drop it everywhere — current state is half-half.

Append-only tables (timeline_notes, documents, ledgers) legitimately have only created_at. This finding is about the editable entity tables.

Proposal: Add updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW() plus the auto-update trigger to every editable entity table that lacks it: customers, vendors, skus, purchase_orders, po_receipts. Append-only tables stay as-is.

Decision: open

A13 — target_type is TEXT + CHECK, not an ENUM

purchase_orders.target_type TEXT NOT NULL DEFAULT 'materials' CHECK (target_type IN ('materials', 'finished_goods')). Inconsistent with the existing materials_inventory_event_type and finished_goods_inventory_event_type ENUMs (and with the new status ENUMs from Q8 revised). Should be a Postgres ENUM (po_target_type or similar).

Proposal: Convert to ENUM org.po_target_type with values materials, finished_goods. Same pattern as Q8.

Decision: open

A14 — to_location_id on ledgers has no ON DELETE specified

materials_inventory_ledger.to_location_id UUID REFERENCES fulfillment_locations(id) — no ON DELETE. Same on FG ledger. The sibling location_id has ON DELETE SET NULL. Defaults to NO ACTION, which prevents location deletion when transfers reference it. Inconsistent — either match location_id's SET NULL or make both RESTRICT deliberately.

Proposal: Match ON DELETE SET NULL on to_location_id for both ledgers. Audit trail still shows the entry happened; lost reference becomes NULL gracefully instead of blocking deletion.

Decision: open

A15 — work_order_items cost columns declared twice

Lines 506-515 declare material_unit_cost / conversion_cost in CREATE TABLE, then lines 520-521 add the same columns via ALTER TABLE ADD COLUMN IF NOT EXISTS. The ALTER block is leftover for back-compat with old DBs that already had the table without these columns. Can be removed if every active DB has been caught up.

Proposal: Drop the redundant ALTER block. Every active DB has the columns now; the back-compat hedge is dead weight.

Decision: open

A16 — is_active coverage is uneven

Master-data tables and entity headers consistently have is_active. Line items (po_items, sales_order_items, work_order_items) and append-only tables don't. The line items are defensibly absent (deactivation lives on the parent), but the design should call out the rule explicitly so we don't sprinkle is_active inconsistently going forward.

Proposal: Document the rule: master-data tables and entity headers carry is_active; line items / receipt items / append-only tables don't. No schema change needed; just make the convention explicit on the org overview.

Decision: open

A17 — code column on ledgers vs ref column

Both inventory ledger tables have both code TEXT and ref TEXT. Memory and the user-actions catalog describe ref as the human reference (PO number, TFR code, etc.). What's code for? Looks like a leftover or undocumented duplicate — needs a code grep to confirm whether it's actually populated/read. If unused, drop it.

Proposal: Investigate (code grep). If code is unused (likely), drop the column. If used, document the distinction from ref here.

Decision: open

A18 — Hex color columns aren't validated

background_color VARCHAR(7), text_color VARCHAR(7) everywhere — no CHECK. A typo writes 'red' and the UI silently breaks. Q8 (revised) moves display config out of the schema entirely (into the application layer), which makes most of these go away — but the columns that remain (e.g., on customer_types, customer_segments, brokers, order_channels, *_types, locations) should either be validated with CHECK (background_color ~ '^#[0-9A-Fa-f]{6}$') or also moved to the app layer.

Decision: resolved by Q10. All color columns get dropped from the schema. Defaults live in the application layer. Nothing left to validate.

A19 — sort_order can be negative

SMALLINT NOT NULL everywhere, no CHECK >= 0. Negative sort orders work but are semantically meaningless. Add CHECK (sort_order >= 0).

Proposal: Add CHECK (sort_order >= 0) on every table that has sort_order.

Decision: open

A20 — Index-existence DO blocks are obsolete

Many indexes are wrapped in DO $$ BEGIN IF NOT EXISTS (SELECT 1 FROM pg_indexes WHERE indexname = '...') THEN CREATE INDEX ...; END IF; END $$; blocks. Postgres ≥ 9.5 supports CREATE INDEX IF NOT EXISTS natively — the DO blocks are dead weight. Cleanup pass to use the native form.

Proposal: Replace every DO-block index guard with native CREATE INDEX IF NOT EXISTS. Cosmetic; cleaner schema file.

Decision: open

Improvements​

A21 — sales_orders.so_number nullable and not unique

Some SO channels don't generate a number immediately, hence nullable. But there's no UNIQUE (org_id, so_number) WHERE so_number IS NOT NULL partial index — duplicates are silently allowed when numbers do exist. Add the partial unique index.

Proposal: Add the partial unique index UNIQUE (org_id, so_number) WHERE so_number IS NOT NULL.

Decision: open

A22 — sales_orders.broker_id lacks an index

Listing "all SOs for this broker" scans. Cheap to add. Probably not load-bearing today but trivial.

Proposal: Add idx_sales_orders_broker_id ON sales_orders(broker_id).

Decision: open

A23 — entity_contacts.entity_type isn't constrained

VARCHAR(100) with comment "Currently used for vendors. Customers support planned for future." Should have a CHECK constraint or ENUM listing valid entity types — as-is, a typo at insert time silently creates an unreachable contact link.

Proposal: Postgres ENUM org.entity_contact_kind with the actually-supported values (customer, vendor, …). Adding a value later = ALTER TYPE ADD VALUE. Pairs with A24.

Decision: open

A24 — entity_contacts polymorphic FK

There's no DB-level guarantee that entity_contacts.entity_id points at a real customer/vendor row. Application-enforced. Worth either accepting the trade-off explicitly (we know it's polymorphic — the convenience outweighs the risk) or moving to per-entity link tables (customer_contacts, vendor_contacts).

Proposal: Accept the polymorphism — N tables for one concept is worse than the orphan risk. Document the rule that the application is responsible for cleanup, and consider an audit job that flags orphans periodically.

Decision: open

A25 — No created_by / updated_by audit columns

No table tracks which user did anything. Manual ledger writes (transfers, adjustments, disposals) lose this audit trail entirely. For a multi-tenant business app this is usually expected. Worth adding created_by UUID REFERENCES platform.users(id) to ledgers and to the major mutable tables — and updated_by where applicable.

Proposal: Add created_by UUID REFERENCES platform.users(id) (nullable, for system-generated rows) on both ledger tables, on transactional headers (PO/WO/SO), and on append-only logs (timeline_notes, documents). updated_by only where updated_at exists.

Decision: open

A26 — delivered_at orphan from the lifecycle pattern

sales_orders.delivered_at DATE exists but isn't part of the documented lifecycle (placed_at → entered_at → shipped_at → invoiced_at → paid_at, with rejected_at for the rejection branch). Either it maps to a status (e.g. Delivered is implicit when fulfillment_status = Fulfilled) or it's dead. Worth grepping the code.

Proposal: Investigate (code grep). If unused, drop the column. If used, decide whether it belongs in the lifecycle date set or with the fulfillment side.

Decision: open

A27 — Denormalized totals can drift

sales_orders.order_value and purchase_orders.costs are denormalizations of the line items × prices. Without a trigger keeping them in sync (or recompute on update), they go stale silently when items change. Either add a maintenance trigger, or remove the column and compute on read.

Proposal: Drop both columns. Compute on read in the API response — a single SUM aggregate is cheap. Triggers add complexity and a class of failures (drift on bulk import, on direct SQL edits).

Decision: open

A28 — Seed pattern is single-org

Default-org status type / fulfillment status / wo_status_types seeds in schema.sql only insert rows for '00000000-0000-0000-0000-000000000001'. A second org has no statuses, no segments, no types, no channels — broken. Today this is fine (single tenant) but is a real bug for multi-tenancy.

The Q8 revision removes status types from this list (they're ENUMs now), but customer_types, customer_segments, brokers, sku_types, material_types, order_channels still depend on per-org seeds. Need a "provision new org" routine that seeds these — design as part of L1.

Proposal: Define a platform.provision_org(org_id) SQL function (or migration-equivalent application routine) that seeds default rows in the org-scoped lookup tables. Q10 simplified the rows — only name + sort_order need defaults. Called once at org creation; idempotent.

Decision: open

A29 — sort_order UNIQUE blocks reorder swaps

UNIQUE (org_id, sort_order) — when reordering, you have to swap via a temporary value or DEFER the constraint, since UPDATE ... SET sort_order=2 then UPDATE ... SET sort_order=1 collides at intermediate state. Was fixed in #333 (the deleted sort-order race fix branch) — worth confirming the fix is still in effect at the design level (e.g. "sort_order columns are reordered via a single UPDATE with a CASE expression, not row-by-row").

Proposal: Make every UNIQUE (org_id, sort_order) constraint DEFERRABLE INITIALLY IMMEDIATE. Reorders use SET CONSTRAINTS ... DEFERRED inside the transaction. Cleaner than the CASE-expression workaround and fully forgiving of any reorder shape.

Decision: open
