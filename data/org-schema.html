Org schema

Tenant-scoped tables. Every row carries org_id UUID NOT NULL REFERENCES platform.organizations(id) for shared-DB isolation. Per-tenant uniqueness is enforced via composite constraints (UNIQUE(org_id, name), UNIQUE(org_id, code), etc.).

There are too many tables in org.* for a single ER diagram to be useful. They're presented here in clusters. Cross-schema FKs to platform.* (status types, organizations) are shown but not redrawn in every cluster — see the cross-schema relationships summary at the end.

Conventions​

  • org_id everywhere. Required for shared-DB isolation. Becomes redundant and is dropped at physical-split time. See Q4.
  • Soft delete via is_active. Most master-data tables expose a soft-delete flag; transactional tables use is_active more sparingly (orders are mostly closed by status, not deactivation).
  • Per-tenant unique constraints. All "natural key" uniqueness is (org_id, ...) rather than just on the column.
  • Renames in this redesign:
    • fulfillment_locations → org.locations (column FKs fulfillment_location_id → location_id, work_site_id keeps its name as a semantic alias). See Q9.
  • Status type FKs cross schemas. Every status_id (PO, WO, SO order_status, SO fulfillment_status) references the canonical platform.<x>_status_types table — no per-org status_type lists in org.*. See Q8.

Master data​

The reusable entities the rest of the org schema points at: parties, items, locations, channels, contacts.

Parties​

  • org.customers — sales-side party. Carries the rich model: customer_type_id (required, classification), customer_segment_id (segment like Club / Distributor), broker_id + broker_fee_percent (default broker for this customer's SOs), parent_customer_id (hierarchy), country, currency, qbo_id (QBO sync). UNIQUE (org_id, qbo_id).
  • org.vendors — purchase-side party. Flat shape: name, country, address, currency, notes. No types/segments/hierarchy by design — see Q7.
  • Customer master-data lookups: customer_types, customer_segments, brokers. All same shape (id, org_id, name, sort_order, colors, is_active) with UNIQUE(org_id, name) and UNIQUE(org_id, sort_order).

Products & materials​

  • org.skus — finished goods. sku_code (UNIQUE per org), name, sku_type_id, items_per_unit (≥1), oz_per_item (optional).
  • org.materials — raw inputs. material_code (UNIQUE per org), name, material_type_id. Materials and SKUs are kept separate — see Q6.
  • org.sku_types, org.material_types — classification tables, same shape as the customer-side type tables.

Locations​

  • org.locations (renamed from fulfillment_locations) — used as PO ship-to, WO work site, SO fulfillment location, and inventory bin. name, address, country, email (UNIQUE per org), phone, sort + colors. See Q9.

Channels​

  • org.order_channels — sales channel classification (Direct, Distributor, etc.). Required on every SO.

Contacts​

Org-private pool of people, with email/phone methods, linkable to any entity (customer, vendor, etc.). See Q5.

  • org.contacts — the person row. display_name, optional first_name/last_name/title, notes.
  • org.contact_methods — emails and phones attached to a contact. method_type SMALLINT CHECK (method_type IN (1, 2)) (1=email, 2=phone), value, label, is_primary. UNIQUE on (contact_id, method_type, value).
  • org.entity_contacts — the link between a contact and any entity. entity_type VARCHAR + entity_id UUID is intentionally polymorphic (no FK at the schema level — the application knows which entity_type strings are valid). role (billing / shipping / sales / ops), is_primary per-entity. UNIQUE on (contact_id, entity_type, entity_id, role).

Bill of materials​

  • org.bom_items — one row per (output SKU × input). sku_id is the output (the SKU this BOM produces). Either material_id or input_sku_id is set, never both — enforced by a CHECK constraint. The same constraint also forbids input_sku_id = sku_id (no self-referential BOM). quantity NUMERIC(18,6) allows decimals (post-#329).

Purchase orders​

  • org.purchase_orders — header. po_number UNIQUE per org. target_type ∈ ('materials', 'finished_goods') chooses which input table the line items reference. status_id → platform.po_status_types.
  • org.po_items — line items. material_id XOR sku_id enforced by CHECK; the choice must match the parent PO's target_type (application-level invariant, not schema-enforced).
  • org.po_receipts + org.po_receipt_items — actual receipts. Same XOR shape on receipt items.

Work orders​

  • org.work_orders — header. wo_number UNIQUE per org. work_site_id → org.locations (renamed FK column). status_id → platform.wo_status_types.
  • org.work_order_items — outputs the WO produces. WO inputs (which materials get consumed to produce these SKUs) are derived via bom_items, not stored on the WO.
  • org.work_order_receipts + org.work_order_receipt_items — actual production receipts driving the FG ledger.

Sales orders​

  • org.sales_orders — header. Two status FKs: order_status_id → platform.order_status_types and fulfillment_status_id → platform.fulfillment_status_types. Lifecycle dates (placed_at, entered_at, shipped_at, invoiced_at, paid_at, rejected_at) drive UI, not status logic.
  • org.sales_order_items — line items. UNIQUE on (sales_order_id, sku_id) — one line per SKU per SO.
  • org.sales_order_timeline_notes — audit-style notes pinned to a status.
  • org.sales_order_documents — files attached to the SO. url points to GCS.

Inventory ledgers​

Append-only event logs. The summary views ("on-hand by item × location") are derived, not stored.

  • org.materials_inventory_ledger — one row per materials movement. event_type materials_inventory_event_type (Postgres ENUM): ORDER, RECEIVE, TRANSFER, ADJUST, DISPOSE, ALLOCATE, CONSUME. ref is the human-facing reference string (PO number, TFR code, etc.); source_type + source_id is the structural pointer back to the originating row, used as an idempotency key by reconciliation.
  • org.finished_goods_inventory_ledger — same shape, anchored on sku_id instead of material_id. Different ENUM: ORDER, RECEIVE (from PO or WO), TRANSFER, ADJUST, DISPOSE, ALLOCATE, CONSUME (from SO fulfillment).

Cross-schema relationships​

The FKs that cross the platform↔org boundary, all in one place.

Two patterns of cross-schema FK:

  1. Tenancy anchor. Every org.* table's org_id references platform.organizations(id). Drops at physical-split time when each org gets its own DB.
  2. Status type lookups. Transactional tables in org.* reference the canonical lists in platform.<x>_status_types. These references survive physical split as cross-DB FKs (or, more likely, as application-enforced lookups against a cached read of the platform DB).
