Endpoint review questions

Context for the reviewer​

This page collects the open design decisions for the Pharus public API (Layer 4 / "L4") that need a human call before they get locked in. It is the L4 counterpart to the L3 review questions and belongs to GitHub issue #353 (Stage A, Task 6).

Where this fits. Pharus has four design layers:

  1. L1 — Data model. Postgres tables (platform / org split).
  2. L2 — Domain components. Thin DB-access APIs, one per entity (PurchaseOrders, MaterialsInventory, …).
  3. L3 — Business logic. 177 workflows (W001–W177) that compose L2 components, enforce constraints, and own the unit of work behind every user action.
  4. L4 — Public API. 177 HTTP endpoints (E001–E177), one per workflow, aligned 1:1 so E020 calls W020.

L1, L2, and L3 are already designed and locked. L4 is what this PR designs, and the page you're reading is the last step before the design is approved.

What's already decided in L4 (these don't need answers — they're listed so you have the surrounding picture):

  • REST over HTTP/JSON, methods GET / POST / PATCH / DELETE, no PUT.
  • One endpoint per L3 workflow, same E### ↔ W### numbering.
  • Spec lives as structured markdown now; conversion to OpenAPI is an implementation-phase task, not part of this design.
  • Auth carries over from today: Authorization: Bearer <firebase-id-token> + X-Org-Id middleware sets req.authUser / req.orgId.
  • Access checks (member / admin / owner) live at L4 so L3 stays role-agnostic.
  • Request validation with Zod at the L4 boundary; L3 receives already-typed input.
  • L3 typed errors map to HTTP: NotFoundError → 404, InvalidTransitionError → 409, ValidationError → 422.
  • No idempotency keys in v1.0.0.

What you're being asked to do here. Read each question, pick one of the listed options (or propose a new one), and your answer becomes the locked decision. Each question has a default that's already implemented in the docs — saying "go with the default" is a valid answer. Questions are grouped into cross-cutting (apply across the whole API) and per-domain (apply to one specific area).

Status field. "Open" = waiting for your answer. "Locked" = decided.

Open design calls and trade-offs from the L4 design. Each question is locked once an answer is recorded; reviewers can disagree and reopen any item until it's marked Locked. Mirrors the structure of the L3 review questions.

Cross-cutting (Round 1)​

Q-R1-1: Pagination — cursor vs. offset?​

Status. Open.

Context. The overview proposes cursor pagination (?cursor=<opaque>&limit=<int> → { data, nextCursor }) as the default. Cursor pagination handles concurrent writes during long scrolls without dropping or duplicating rows; offset is easier to jump-link but degrades on large tables and isn't stable against insertions. List endpoints in scope: POs, WOs, SOs, customers, vendors, materials, SKUs, contacts, ledger entries. Bounded lookups (status types, channels, segments, brokers, locations) don't paginate either way.

Options.

  • Cursor (overview default). Stable across writes; opaque ID; no random-access jumps.
  • Offset (?page=<n>&limit=<int>). Familiar from the current Pharus UI; supports "jump to page 7". Less stable as the dataset moves under the user.

Q-R1-2: Versioning — path prefix vs. header vs. unversioned in v1.0.0?​

Status. Open.

Context. Overview proposes /api/v1/... for every endpoint. Breaking changes get /api/v2. Alternative: ship v1.0.0 unversioned (just /api/...) and introduce versioning only when the first breaking change lands. With a single template (Anthem) and a single frontend client, the practical cost of unversioning is low; the cost of getting locked into the wrong scheme is also low because there are no third-party consumers yet.

Options.

  • /api/v1 (overview default). Future-proof, but the v1 marker is paid up-front by every URL forever.
  • /api only in v1.0.0; add /v2 when needed. Cheaper today; commits to a renaming step the first time a breaking change ships.

Q-R1-3: Frontend type sharing — @pharus/api-contracts workspace package, or generate from OpenAPI now?​

Status. Open.

Context. Overview proposes a @pharus/api-contracts workspace package: Zod schemas + inferred TS types, imported by both backend (parse on the way in) and frontend (consume types). OpenAPI generation is deferred to implementation Task 11. The alternative is to author OpenAPI now and generate the package from it — more tooling upfront, single source of truth.

Options.

  • Workspace package now, OpenAPI later (overview default). Faster path through Stage A; lets us iterate the schemas without bouncing through codegen.
  • OpenAPI as the source of truth from day one. Higher friction during the design phase, but no later conversion step and clean third-party consumer story.

Q-R1-4: Soft-delete return shape — 200 + entity or 204 No Content?​

Status. Open.

Context. Several DELETE endpoints (E126 SKU, E142 vendor, E149 material) are soft delete — they flip isActive to false and the row sticks around. The pages return 200 OK with the updated entity so the UI can refresh the row's badge without a follow-up GET. Hard-delete endpoints (E022 PO, E105 customer, E161 location) return 204 No Content in line with REST defaults. The inconsistency may be worth keeping (different semantics, different signals) or worth ironing flat.

Options.

  • Keep the split (current design). 200 + entity for soft delete, 204 for hard delete. The shape signals the semantics.
  • 204 everywhere. Uniform; the UI re-fetches the row after a soft delete. Slightly more chatty.
  • 200 + entity everywhere. Lossy on hard delete (entity no longer exists), so the response carries an { deletedId } echo instead.

Q-R1-5: Codes immutable after create on master records?​

Status. Open.

Context. Per the per-domain detail, code is immutable on SKU, vendor, material, and location after create. The reasoning: codes are used as denormalized references in ledger ref values, bulk-import payloads, and CSV exports, so editing one would orphan history. The L3 workflows don't currently express this — it surfaced as a per-endpoint design call in L4.

Options.

  • Immutable (current design). Safer for history; requires an "archive and recreate" loop when a user needs to rename a code.
  • Mutable with history. Allow code edits; the L2 op writes the old code to a code_history table so ledger lookups can resolve old refs.

Q-R1-6: File uploads — multipart vs. base64-in-JSON vs. signed-URL PUT?​

Status. Open.

Context. Two upload endpoints in Stage A: E004 (org logo, via PATCH /organizations/current) and E067 (SO documents). Both default to multipart/form-data per the overview. Alternatives: base64-in-JSON (keeps the API JSON-pure, but inflates payload ~33% and breaks streaming) or two-step signed URL (POST /uploads/sign returns a GCS URL, frontend PUTs directly, then POST /sales-orders/:id/documents references the upload — keeps the server out of the byte path).

Options.

  • Multipart (overview default). One round-trip; bytes flow through the API.
  • Signed URL. Two round-trips but server doesn't touch bytes; better for large files.
  • Base64 in JSON. Uniform JSON shape; bad fit for anything over ~5 MB.

Q-R1-7: Error envelope — { error: { code, message } } or RFC 7807 application/problem+json?​

Status. Open.

Context. Overview proposes { error: { code, message, details? } } with HTTP status from L3 typed errors. RFC 7807 (type, title, status, detail, instance) is a standard for HTTP error responses with broader tooling support. The proposal is simpler but non-standard.

Options.

  • { error: { code, message } } (overview default). Compact; code is the machine identifier.
  • RFC 7807. Standardized; verbose; more familiar to consumers wired to other APIs.

Q-R1-8: 410 Gone for expired invitations (E018) — fit or overreach?​

Status. Open.

Context. E018 (look up invitation by token) returns 410 Gone when the invitation is expired, accepted, or revoked. Most expired/consumed states across the API map to 409 invalid_transition; 410 is reserved here because the resource is intentionally unreachable forever. The split may be worth keeping (semantic precision for a public-token route) or may be inconsistent with the rest.

Options.

  • Keep 410 on E018 (current design). Public token routes deserve the precise "this URL is permanently gone" signal.
  • Use 409 everywhere. Uniform with the rest of the API; consumers route on code not status.

Per-domain (Round 1)​

Q-PO-1: PO PDF behavior when org branding is incomplete?​

Status. Open.

Context. E039 currently surfaces 422 validation_failed when org branding (logo, billing address) is incomplete, on the rationale that the PDF would be unusably blank in spots. Alternative: render the PDF with placeholders for missing fields and return it anyway, surfacing a non-blocking warning header. The user-facing experience differs: hard fail with a "set up branding first" CTA, or soft-render with gaps.

Options. Hard-fail (current), soft-render with warning, soft-render without warning.

Q-WO-1: Insufficient FIFO coverage on receipt — block or partial-consume?​

Status. Open.

Context. E046 (WO receipt) currently surfaces 409 invalid_transition if the FIFO layers at the site location can't cover the requested consumed quantity. Alternative: consume what's available and surface the shortfall in the response so the user can decide. The current behavior matches the L3 W046 design but is worth flagging because in practice users will hit this.

Options. Block (current), partial-consume with response shortfall, partial-consume with a 409 + already-written entries.

Q-SO-1: Document upload — size and type limits?​

Status. Open.

Context. E067 surfaces 422 validation_failed "if file exceeds size / type limits" but the limits aren't named. The implementation needs concrete numbers. Common defaults: 10 MB per file, mimeType in { pdf, png, jpg, csv, xlsx }.

Options. 10 MB / PDF + image + spreadsheet, 25 MB / any mimeType, smaller / stricter list.

Q-CONT-1: Polymorphic entityType set — { customer, vendor } only, or broader?​

Status. Open.

Context. E170 / E171 / E172 / E177 take entityType as "customer" or "vendor" only. The L3 W170 design matches this. Possible extensions: broker (so brokers can have their own primary contact), location (site contact), organization (org-level billing contact).

Options. Keep { customer, vendor } (current), add broker, add broker + location, add broker + location + organization.

Q-MI-1: ADJUST that would drive balance negative — block or allow with audit flag?​

Status. Open.

Context. E091 / E098 surface 422 validation_failed if the delta would drive the per-(material/sku, location) balance below zero. Alternative: allow the negative balance (audit / count-correction reality is sometimes negative on paper, reconciled later) and flag it on the ledger entry.

Options. Block (current), allow with isNegativeBalance: true flag on the entry, allow + require a reason code.

Q-FG-1: SO cancellation reverse entries — automatic or two-step?​

Status. Open.

Context. E059 (status → Cancelled) automatically writes REVERSE_DEMAND entries for every unshipped item per W059. The trigger is implicit in the status transition. Alternative: require an explicit cancelAndReverse: true flag in the body, or split into a dedicated POST /sales-orders/:id/cancel endpoint with its own request body.

Options. Keep implicit (current), require explicit flag, dedicated endpoint.

Q-LOC-1: Location in-use sample shape — is the broad sampleRefs object worth it?​

Status. Open.

Context. E163 returns { inUse, sampleRefs: { soIds, poIds, woIds, ledgerEntryIds } } — a broader shape than the other in-use checks (which return a single samples*Ids array). Locations are referenced everywhere, so the broader shape is justified, but it's an inconsistency.

Options. Keep broad (current), narrow to a single sampleRefs: [{ kind, id }] array, narrow to a single array of ids regardless of kind.
