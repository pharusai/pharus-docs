Endpoint review questions

Context for the reviewer​

This page collects the open design decisions for the Pharus public API (Layer 4 / "L4") that need a human call before they get locked in. It is the L4 counterpart to the L3 review questions and belongs to GitHub issue #353 (Stage A, Task 6).

Where this fits. Pharus has four design layers:

  1. L1 — Data model. Postgres tables (platform / org split).
  2. L2 — Domain components. Thin DB-access APIs, one per entity (PurchaseOrders, MaterialsInventory, …).
  3. L3 — Business logic. 177 workflows (W001–W177) that compose L2 components, enforce constraints, and own the unit of work behind every user action.
  4. L4 — Public API. 177 HTTP endpoints (E001–E177), one per workflow, aligned 1:1 so E020 calls W020.

L1, L2, and L3 are already designed and locked. L4 is what this PR designs, and the page you're reading is the last step before the design is approved.

Round 1 status. Locked on 2026-05-19. All 8 cross-cutting and 7 per-domain questions have decisions; the relevant endpoint and overview pages are being updated to match.

Cross-cutting (Round 1)​

Q-R1-1: Pagination — cursor vs. offset?​

Status. Locked — Cursor.

Decision. Cursor pagination on every list endpoint (?cursor=<opaque>&limit=<int> → { data, nextCursor }). Stable against concurrent writes, no repeats or gaps, handles filters and sorting cleanly. Bounded lookups (status types, channels, segments, brokers, locations) still return the full list without pagination.

Q-R1-2: Versioning — path prefix vs. unversioned in v1.0.0?​

Status. Locked — Unversioned in v1.0.0.

Decision. Ship clean URLs now (/api/...); retrofit a /v1 prefix later if external clients or third-party integrations require it. The cost of unversioning is low while we have one frontend and one template; the cost of carrying a vestigial /v1 everywhere is paid by every URL forever.

Q-R1-3: Frontend type sharing — @pharus/api-contracts package vs. OpenAPI from day one?​

Status. Locked — OpenAPI as the source of truth from day one.

Decision. Author endpoints as OpenAPI; generate the Zod schemas and the TypeScript types from the spec. Agent-first design (Pharus is being built for AI-first usage) requires machine-readable contracts, and the OpenAPI artifact is the cheapest way to expose them. The @pharus/api-contracts workspace package becomes a consumer of the generated output, not its source.

Q-R1-4: Delete return shape — 200 + entity, 204, or 200 + { deletedId }?​

Status. Locked — 200 OK for all deletes.

Decision. Every DELETE returns 200 OK. Soft deletes return the updated entity (so the UI can refresh the row's badge without a follow-up GET). Hard deletes return { deletedId: "uuid" } as an echo. No 204 responses in the API.

Q-R1-5: Codes immutable after create on master records?​

Status. Locked — Immutable.

Decision. code is immutable after create on SKU, vendor, material, and location. Renaming a code orphans denormalized references in the ledger (ref values), bulk-import payloads, and CSV exports. Users who need to "rename" archive the row and create a new one.

Q-R1-6: File uploads — multipart vs. base64-in-JSON vs. signed-URL PUT?​

Status. Locked — Multipart form-data for the one true file upload (E067).

Decision. Only one endpoint in Stage A is a real file upload: E067 (Upload document to sales order). It uses multipart/form-data so bytes flow through the API, the server keeps full audit control, and we stay decoupled from any specific cloud provider's signed-URL scheme. E004 (Update organization) is not a multipart upload — it takes a logoUrl: "https://..." string in JSON (the frontend uploads to its storage of choice and PATCHes the resulting URL); the original framing of Q-R1-6 around E004 was wrong.

Q-R1-7: Error envelope — { error: { code, message, details? } } vs. RFC 7807?​

Status. Locked — Custom { error: { code, message, details? } }.

Decision. Standardize the L4 shape now; the L3 typed-error hierarchy is still maturing and RFC 7807's type / title / instance fields don't carry useful information for our consumers yet. Migration to RFC 7807 stays available later if external integrations need it.

Q-R1-8: 410 Gone for expired invitations (E018)?​

Status. Locked — Use 409 everywhere.

Decision. Drop the 410 special case on E018. Expired / revoked / accepted invitations surface as 409 invalid_transition like every other "this resource exists but you can't have it" condition in the API. Consumers route on code, not status.

Per-domain (Round 1)​

Q-PO-1: PO PDF behavior when org branding is incomplete?​

Status. Locked — Soft-render with placeholders and a warning.

Decision. E039 returns the PDF regardless of branding completeness. Missing logo / billing-address fields render as placeholders. The response includes a X-Pharus-Warning: branding_incomplete header (and the warning surfaces in the structured response wrapper when E039 is invoked via an OpenAPI client). The L4 page's validation_failed error case is removed.

Q-WO-1: Insufficient FIFO coverage on receipt — block or partial-consume?​

Status. Locked — Block.

Decision. E046 returns 409 invalid_transition when FIFO layers at the site location can't cover the requested consumed quantity. No partial writes. Users who hit this can split the receipt manually after staging more materials.

Q-SO-1: Document upload — size and type limits?​

Status. Locked — 10 MB per file; mimeType in { pdf, png, jpg, csv, xlsx }.

Decision. E067 rejects files larger than 10 MB or with mimeTypes outside { application/pdf, image/png, image/jpeg, text/csv, application/vnd.openxmlformats-officedocument.spreadsheetml.sheet }. Both checks surface as 422 validation_failed with a descriptive message.

Q-CONT-1: Polymorphic entityType set?​

Status. Locked — { customer, vendor } only.

Decision. Keep the polymorphic entityType constrained to "customer" and "vendor" in v1.0.0. Brokers, locations, and organizations do not link to contacts directly. Extension is a v1.1 conversation.

Q-MI-1: ADJUST that would drive balance negative?​

Status. Locked — Block.

Decision. E091 / E098 return 422 validation_failed when the delta would drive the per-(material/sku, location) balance below zero. Inventory cannot go negative in this design. Reason: a negative balance breaks FIFO unit-cost lookups downstream, which the cost cascade and ledger reports both depend on. ADJUST itself accepts either a positive or a negative delta — the rule is only about the resulting balance, not the sign of the input.

Q-FG-1: SO cancellation reverse entries — implicit or explicit?​

Status. Locked — Implicit.

Decision. E059's status transition to Cancelled automatically writes REVERSE_DEMAND entries against every unshipped item per W059. No explicit cancelAndReverse: true flag, no separate cancel endpoint. The reverse is part of the cancellation contract.

Q-LOC-1: Location in-use sample shape?​

Status. Locked — Keep the broad object.

Decision. E163 returns { inUse, sampleRefs: { soIds, poIds, woIds, ledgerEntryIds } }. The broader shape is justified by location cardinality — a single location touches sales, purchasing, production, and inventory simultaneously, so the consumer wants to know where the references are, not just that they exist.

Doc inconsistencies resolved alongside Round 1​

Three spots where the per-domain detail pages disagreed with the locked decisions or with themselves; all three are being patched in the same commit as the lock:

  • E126 / E142 / E149 (soft-delete + in-use). These endpoints are soft delete only — they flip isActive to false and always succeed. The 409 in_use row is removed from their error tables. Hard deletes are not exposed at the API surface; they're DB-only operations.
  • E091 / E098 ADJUST direction. Spec now explicitly says positive and negative deltas are allowed. The validation rule is on the resulting balance, not the sign of the input.
  • E004 logo upload. Body takes a logoUrl: "https://..." string. There is no multipart upload at this endpoint; Q-R1-6's framing is corrected above.
